口径说明：本稿是交互行为基线（点了什么、状态怎么变），不是视觉/控件基线。 下面三张卡里的控件名是 v1 遗留写法（如内容可编辑重命名、GtkCheckButton、窗口内遮罩对话框）； 最终控件映射与视觉以 `docs/tech-stack.md` §4.5/§4.6 为准（AdwEntryRow、AdwSwitchRow、 AdwNavigationView push 页、跟随系统主题、不写自定义 CSS）。两者冲突时按 §4.6 裁决表执行。

屏1 · 应用列表 — 组件映射与状态

窗口 / 头栏AdwWindow + AdwHeaderBar（CSD 圆角、居中粗体标题、右侧窗控圆点）
页面骨架AdwPreferencesPage → AdwPreferencesGroup → boxed AdwActionRow
搜索GtkSearchEntry——397 个应用翻不到，按显示名 + desktop id 双字段过滤。已开启组常驻不过滤（方案设计 §6.1.1）
分身开关AdwSwitchRow——已开启与未开启用同一套控件，开关是唯一主入口；点亮 = 按档案状态分派（不是按"有没有实例"）：无档案 → 首次配置（跑探测）、档案失效 → 重新配置（跑探测+重建档案+建实例）、有档案且可用 → 开启分身（复用档案、跳过探测）；关闭 = AdwAlertDialog 确认（删该应用全部实例数据），取消则回弹；有实例在跑时关闭被拒绝（与 rm 退出码 7 一致）
所有应用未开启的一行一个 AdwSwitchRow（不进详情，没有实例可管）；无搜索词时只渲染前 30 个，组尾「显示全部 N 个应用」——AdwPreferencesGroup 不是虚拟化列表，400 行要分页（ADR-024）；搜索命中封顶 100 条并提示"再输几个字"，且输入 120ms 防抖
来源说明系统级 / 用户级 / Flatpak 三个目录（只写用户级会漏 97% 的应用）
状态：默认空态（AdwStatusPage 取代「已开启」组，列表照常）致命横幅（bwrap 缺失 → 开关全部失效）降级横幅（fuse 缺失，可「了解」）搜索无结果副标题显示实例数与「N 个运行中」
跳转：点行体 → 屏2 详情；点亮开关 → 屏3（首次配置 / 重新配置 / 开启分身）；关闭开关 → 确认对话框。
空态不能把列表藏掉：首启用户看到"尚未开启任何分身"却被指去一个不存在的区域，等于无路可走。空态只取代「已开启分身」这一组。

屏2 · 应用详情 — 组件映射与状态

实例行AdwActionRow + 尾部按钮组：启动（suggested）/ 删除（destructive-flat）；运行中两个都禁用（rm 对运行中实例一律拒绝，退出码 7，界面不能比 CLI 宽松）
运行状态读 instances/<app>/<id>/run.lock 的 flock（拿不到锁 = 在跑），不用 pgrep、不用 PID 文件（方案设计 §4.3）
重命名AdwEntryRow（GNOME 原生表单模式；本稿为演示用 contenteditable，原生不用它）。只改 display_name，id 创建后不可变
新建入口AdwActionRow（activatable）→ 屏3（新建分身，沿用现有档案、跳过探测）
档案组AdwPreferencesGroup 只读行：隔离路径数、探测方式与置信度（只说证据来源与覆盖范围，不写"结果完整"/"全部已捕获"）、单例处理、共享但可写（`shared_writes`，说清"两个分身的最近文件会混"这种代价）、最近一次审计结论、实例根目录
删除确认AdwAlertDialog：标题点名实例、正文说明「移入回收站」；default response 是「取消」——把「移到回收站」设成默认等于回车即删（键盘用户一按就没了），对话框存在的意义正是"不要一键删"
操作反馈AdwToast——创建/重命名/删除结果不打断列表，不用模态弹窗报成功。**一次只显示一条，新的顶掉旧的**，所以 toast 只承载一次性确认，关键结果必须同时体现在行内
状态：有实例零实例（仅剩「新建分身」行）有实例运行中删除确认中
跳转：头栏「←」→ 屏1；「新建分身」→ 屏3（clone）；「重新探测」→ 屏3（rediscover，只更新档案不建实例）。
Esc 三级语义：确认框开着 → 只关确认框；探测页开着 → 关探测页（等同取消）；都没有 → 不做导航（Esc 不是"返回"，返回走头栏「←」）。

屏3 · 探测页 — 四态与四组

承载原生为 AdwNavigationView 的 push 页（不是对话框）；本稿用遮罩对话框表达同一状态机
闸门（探测前）四道闸门跑在探测会话启动之前：bwrap 不可用 / 缺 fuse（降级不阻断）/ 目标应用还在运行 / 拿不到全局写锁。硬闸门失败直接进 error 并带原因，不启动会话
探测中GtkSpinner + 「正在跟踪写入…」+ 已发现 N 个写入条目（流式递增）+ HeaderBar「取消探测」——取消必给，探测十秒到一分钟。措辞是"条目"不是"命中次数"：overlay 只知道"写过/删过"，拿不到次数
确认四组：① 应用自身数据（可勾 AdwSwitchRow，缓存项也在这组、默认不勾并标「缓存」）② 单例处理（可勾 AdwSwitchRow：私有 runtime / 私有 DBus，由检出的单例项驱动、没检出就不出现；本稿用 app.singleton 演示——firefox/chrome/notion 就没有这一组）注意：本稿把 ~/.dingtalk、~/.mozilla 这类顶层点目录标成「配置」且默认勾选，只是演示；真实 L2 规则里它们是灰区、默认不勾（discover.md §5 第 5 条）。照抄会把用户自己放在点目录里的文件误判成应用数据。
③ 公共目录（强制共享）：只读 AdwActionRow + .dim-label，一律显示、不可勾 ④ 共享但可写（不隔离）：只读，并写清代价（"两个分身的最近文件会混在一起"）——不说，用户遇到就判定产品坏了
创建中独立第四态，不是"confirm 里加个 flag"：写档案 + 建实例目录 + 生成 .desktop 是几百毫秒的事务，期间再点一次确认会建出两个实例；中途取消会留下"档案写了、实例没建成"的半成品。故：确认按钮变「正在创建…」并禁用，取消也禁用，Esc 同样不生效
失败AdwStatusPage：按 Reason 分文案——app_running / env_unavailable / no_writes / public_dir_leak，每类一条独立键与"下一步做什么"；禁止所有失败共用一句"探测失败"。「这次没有跟踪到任何写入」也走这一态，不生成空档案
确认按钮suggested-action：创建分身（setup/reconfig/clone）/ 开启分身（open）/ 保存档案（rediscover）；门禁只数「应用自身数据」——只勾缓存或单例时仍禁用，否则会生成一个什么都不隔离的空档案；探测中与创建中该按钮不存在/不可用
失败态的「重试」恒可用——不能沿用上一轮 confirm 的 disabled。失败态只有「重试」与「取消」两条出路，一个点不动的重试等于让用户关窗口
降级横幅对话框里另有一条 AdwBanner：窗口顶部那条已被遮罩盖住。列表那条可「了解」收掉，这条不能——降级是事实，不是通知
态：probingconfirmcreatingerror　入口：首次配置（无档案）重新配置（档案失效）开启分身（档案可用）新建分身（详情页 ＋）重新探测
入口标题必须点名当前在做哪件事：从没配过才叫「首次配置」（要跑探测），配过但关掉了叫「开启分身」（复用档案、跳过探测）， 配过但档案里的路径已不存在叫「重新配置」（要重探，但不能复用失效档案——复用等于造一个启动即报错的分身）。 把"配过但关掉了"说成首次配置，用户会以为之前的档案白做了，还白等一分钟探测。五个入口 → 五个标题，不靠"有没有实例"猜。 确认 → creating → 写档案 + 建实例 + Toast；取消 → 什么都没发生（档案不写、实例不建、临时区清空）。
