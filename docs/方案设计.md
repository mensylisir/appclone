# Linux 应用分身（App Clone）方案设计

> 目标：在桌面 Linux 上实现类似 Android "应用分身 / Cloned Apps" 的功能——
> **只隔离目标应用自身的配置与数据**（两个实例互不可见、可同时运行），
> **其余一切照常共享**（下载、文档、剪贴板、通知、输入法、GPU/音频）。
> 无需 root，无需修改应用本身。

**文档体系与版本定位**

| 文档 | 内容 |
|---|---|
| 本文（方案设计） | 需求定义、隔离机制、目录布局、档案规范、验证清单——跨视图稳定的设计契约 |
| [tech-stack.md](tech-stack.md) | 技术选型与 ADR：引擎（bubblewrap）、实现（Go，唯一路径）、GUI（gotk4） |
| [discover.md](discover.md) | 路径自动探测方案（ADR-008） |

实现形态：**Go 单仓库**（`core` + `cmd/appclone` CLI + `cmd/appclone-gui` GUI），
产品直达普通用户（GUI 为主入口，CLI 服务开发者）。本文定义的命令语义、
实例目录布局、档案字段语义是 CLI/GUI 双视图共同遵守的契约，与视图无关；
选型理由一律见 tech-stack.md。早期 bash 原型（`legacy/`）仅用于隔离语义验证，
不属于产品路径（ADR-002）。

## 1. 设计目标与非目标

**目标**

- 同一应用多个实例并行运行，各有独立账号/聊天记录/设置；
- 实例间私有数据互不可见（含内核层面的 mount 隔离）；
- 公共文件（`~/Downloads` 等）与会话资源全部共享——分身下载的文件直接出现在原位置；
- 对应用黑盒：不依赖应用支持多开参数；
- 一条命令创建/删除分身，并生成带角标的桌面图标（近似 Android 的"开关"体验）。

**非目标（当前版本不做）**

- 强权限隔离（分身进程拿不到主实例数据的访问权）——那是 user namespace + 独立 UID 的路线，复杂度高且引入桌面会话授权问题；
- Flatpak 应用内部分身（另有思路，见 §8.4）；
- Windows/Wayland 单显示会话外的多桌面环境。

## 2. 与 Android Cloned Apps 的机制对照

| Android（多用户机制） | 本方案（mount namespace） |
|---|---|
| `installExistingPackageAsUser(pkg, profileId)`，数据目录自动出现在 `/data/user/<id>/<pkg>/` | 档案 `AC_PATHS` + `--bind 实例目录 原路径`，数据目录重定向到 `instances/<app>/<id>/root/` 下 |
| PMS 安装时**统一分配**数据目录（路径确定，所以一个开关即可） | Linux 无"户籍管理"，用 per-app **路径档案**事后补齐这份知识 |
| AMS 按 userId 检测单实例 | 私有 DBus 会话总线 + 锁文件 inode 替换 |
| Launcher 显示两个图标 | 自动生成 `.desktop`（Name 加「分身」后缀） |
| 克隆 profile **共享**父用户外部存储 `/storage/emulated/0` | `--bind / /` 整个根文件系统原样透传，天然共享 |

## 3. 总体架构

分身执行链（对两个版本一致）：

```
桌面入口  appclone-<app>-<id>.desktop
   │
   └─ appclone run <app> <id>            ← CLI 视图（GUI 是同一 core 的另一视图）
        ├─ core：加载档案  profiles.d/<app>（路径知识库 = 事后补做的 Android PMS 安装期目录分配）
        ├─ core：构造 bwrap 参数（BuildBwrapArgs —— 项目的事实核心，纯函数）
        │      --bind / /                      ← 整个系统原样透传（其余全部可见）
        │      --bind 实例私有目录 应用数据路径   ← 仅偷换应用自己的目录
        │      --bind 实例私有空文件 应用锁文件    ← 绕过互斥锁
        │      （可选）私有 DBus session bus
        │      （可选）私有 XDG_RUNTIME_DIR（wayland/pulse socket 仍共享进来）
        └─ exec bwrap ... -- <应用可执行文件>
```

**不做前后端分离**：无 daemon、无 IPC 协议。CLI（cobra，开发者视图）与 GUI
（gotk4，普通用户主入口，见 tech-stack.md ADR-004/005）是同一 core 的两个薄视图，
GUI 崩溃不影响 CLI 功能完整性。

**核心原理一句话**：进入一个私有 mount namespace，在里面把整个文件系统原样 bind 进来，只把应用读写自身状态的那几个目录换成分身专用的副本。替换仅存在于该进程的命名空间内，主用户环境零影响，不需要 root。

## 4. 目录与文件布局

```
~/.local/share/appclone/
├── profiles.d/
│   └── <app>.toml         # 应用档案：exec、paths、lock_files 等（见 §5.3）
├── instances/
│   └── <app>/<id>/
│       ├── root/<原路径>/   # 偷换后的数据目录（如 root/home/u/.config/WeChat/）
│       ├── locks/           # 私有锁文件
│       └── runtime/         # （可选）私有 XDG_RUNTIME_DIR
├── .trash/                  # 删除实例的兜底存放处
~/.local/share/applications/
└── appclone-<app>-<id>.desktop   # 生成的桌面入口
```

**契约性质**：本布局是 CLI/GUI 双视图共用的事实标准——互操作优先于格式洁癖。

## 5. 应用档案（per-app 路径知识库）规范

这是整套方案中唯一需要人工维护的东西，也是 Linux 与 Android 架构差异的落点（Android 由系统在安装期统一分配目录，Linux 需要事后摸清）。

| 字段 | 说明 |
|---|---|
| `exec` | 应用可执行文件路径（必填，由 `.desktop` 自动解析） |
| `paths` | 需要隔离的目录列表（探测结果填入；支持 `$HOME` 展开） |
| `lock_files` | 应用用于互斥的锁文件/socket 路径，将被替换为实例私有空文件 |
| `extra_binds` | 额外 bind，格式 `"源|目标"`，用于 `/var`、`/opt` 下写死的路径 |
| `isolate_dbus` | true = 私有 DBus 会话总线，绕过 well-known name 单例检测 |
| `isolate_runtime` | true = 私有 XDG_RUNTIME_DIR（wayland/pulse/bus socket 仍 bind 进来） |
| `env` | 额外环境变量，`"VAR" = "value"` |
| `cwd` | 启动工作目录 |

### 5.1 档案示例：通用 Electron 应用模板（`profiles/someapp.toml`）

```toml
exec = "/usr/bin/some-electron-app"
paths = [
  "~/.config/SomeApp",
  "~/.local/share/SomeApp",   # 部分应用还写 ~/.SomeApp，以探测结果为准
]
lock_files = ["$XDG_RUNTIME_DIR/someapp.sock"]   # Electron 常见的单例 socket
isolate_dbus = true    # 若应用在 DBus 上抢 well-known name
isolate_runtime = false
env = {}
cwd = "~"
```

### 5.2 官方自带多开参数的应用（推荐直接用，不必上沙箱）

```bash
# Chromium 系（含各 Electron 应用）
chromium --user-data-dir="$HOME/appclone/instance2"

# Firefox
firefox -P profile2 -no-remote
```

对这类应用，XDG/专有参数方案比沙箱更干净；appclone 的档案机制留作兜底。

### 5.3 档案格式与生成

- 格式为 TOML（`profiles/<app>.toml`），schema 带 `version` 字段；
- 档案**由探测管线自动生成**（见 [discover.md](discover.md) 三层管线），
  用户只在 GUI 勾选界面确认预判结果，**不要求用户手写任何档案字段**；
- 实例目录布局（§4）不随档案格式变化——升级后既有分身数据原地可用。

## 6. 工具：appclone

产品入口是 GUI（`appclone-gui`，普通用户主入口）；CLI（cobra）服务开发者
与脚本化场景，两者共享 `core`，命令语义一致。安装：

```bash
install -Dm755 appclone ~/.local/bin/appclone
```

依赖：`bubblewrap`（必需）；`strace`、`dbus`、`gio`（可选）。
bwrap 依赖非特权 user namespace，个别发行版需确认
`sysctl kernel.unprivileged_userns_clone` 为 1。

命令语义（CLI 名称与 GUI 操作一一对应，均由 core 承载）：

| 命令 / GUI 操作 | 作用 |
|---|---|
| `appclone add <app> [id]` / 列表页开关 | 探测 → 生成档案 → 创建分身实例 + 桌面入口 |
| `appclone run <app> <id> [args]` / 详情页「启动」 | 在分身环境中启动 |
| `appclone list [app]` / 列表页 | 列出应用与实例 |
| `appclone doctor <app> <id>` | 环境检查，打印将执行的 bwrap 命令（排障） |
| `appclone rm <app> <id>` / 详情页「删除」 | 实例移入回收站 + 删桌面入口 |

### 6.1 产品主流程（普通用户视角）

```
打开 appclone-gui
  → 应用列表自动扫描 ~/.local/share/applications
  → 点开某应用的分身开关
  → 工具自动执行探测管线（用户按提示在应用里把功能用一遍，然后退出）
  → 勾选界面确认预判路径（绝大多数应用只剩 2~3 个预勾选项）
  → 分身图标出现在应用列表，点开即用
```

整个流程中用户**不接触**命令行、档案文件、strace 输出——复杂度全部由
discover 管线（[discover.md](discover.md)）与语义分类消化。
探测的完整方案谱系（overlay-diff 主探测 + 静态预填 + 语义分类三层管线）见该文档。

### 6.2 单例/互斥问题（双开的真正难点）

应用"双开"失败通常不是目录问题，而是单例检测。三种手段由探测管线自动识别
（whiteout / DBus 探测），用户在 GUI 中只看到开关式的处理建议：

1. **锁文件**：探测发现 `flock/open(O_CREAT)` 某固定路径 → 写入 `lock_files`。
   原理：mount 一个 inode 不同的私有空文件盖在上面，`flock` 自然不再互斥。
2. **DBus well-known name**：应用启动时在 session bus 上抢名字，抢不到就把参数
   转发给已有实例后退出 → `isolate_dbus = true`（起私有总线）。
   副作用：托盘、通知等会话集成在分身内失效，GUI 需提示这一取舍。
3. **`$XDG_RUNTIME_DIR` 下的 socket**：Electron 系常见 → `isolate_runtime = true`。
   wayland/pulse/bus socket 会被 bind 进新目录，图形与声音不受影响。

## 7. 验证清单

```bash
# A. 隔离生效：分身写入的数据落在实例目录，而非宿主位置
appclone run <app> <id>   # 在应用内改一条设置，然后：
find ~/.local/share/appclone/instances/<app>/<id>/root -mmin -5
# 宿主对应目录应无新文件

# B. 共享生效：分身下载/保存的文件出现在公共目录
ls -lt ~/Downloads | head        # 分身里保存的文件应在此出现

# C. 双开成立：两实例同时运行
pgrep -af <app>                  # 应看到两个进程

# D. 命名空间内确认替换成功
appclone run <app> <id> sh -c 'findmnt | grep <数据路径>'
# 应显示 bind 类型的挂载
```

## 8. 高级用法

### 8.1 从主实例数据"克隆起步"（OverlayFS 语义）

新分身直接继承主实例现有状态（类似 Android 克隆的复制语义）：

```bash
# 无 root，用 fuse-overlayfs
fuse-overlayfs -o lowerdir="$HOME/.config/WeChat",upperdir=.../instances/wechat/work/upper,workdir=.../work .../instances/wechat/work/merged
# 然后把档案中该路径的 bind 源改为 merged 目录（或临时手工）
bwrap --bind / / --bind .../merged "$HOME/.config/WeChat" wechat
```

分身的修改全落在 upper 层，主实例数据不被触碰。

### 8.2 systemd 逃生舱写法（等价原理，便于临时调试）

```bash
systemd-run --user --same-dir \
  -p BindPaths="$HOME/appclone/wx2/config:$HOME/.config/WeChat" \
  -p BindPaths="$HOME/appclone/wx2/data:$HOME/.local/share/WeChat" \
  wechat
```

### 8.3 仅 XDG 环境变量（应用守规矩时的零成本方案）

```bash
XDG_CONFIG_HOME=$HOME/appclone/inst2/config \
XDG_DATA_HOME=$HOME/appclone/inst2/data \
  some-app
```

### 8.4 Flatpak 应用的思路

Flatpak 已把数据收进 `~/.var/app/<appid>`（相当于平台统一分配目录），
理论上对同一 appid 换实例目录 bind 即可分身；需要 `flatpak run` 与 bwrap 的
嵌套协调，留作后续扩展。

## 9. 局限与风险

- **路径档案需随应用升级维护**：应用改存储位置时分身可能漏隔离——`doctor` 的
  运行时隔离校验可报警并提示重探测，管线重跑即可修复；
- **isolate_dbus 的代价**：私有总线内托盘/通知不可用，适合"能双开 > 桌面集成"的取舍场景；
- **写了 `$HOME` 之外的路径**（如 `/var/lib/x`）：用 `extra_binds` 补；写 `/etc` 的应用已属系统级，不建议分身；
- **不防检测**：与 Android 系统分身不同，本方案目标是"能用"而非"反检测"，风控型应用（银行类）理论上可经环境探查发现 mount namespace；
- **多实例资源占用**：每个分身是完整进程（含独立渲染进程），内存按实例数增长，与 Android 同理；
- **非特权 user namespace 被禁的环境**（部分企业策略）bwrap 无法运行，需改用 root 挂载或 systemd-run 变体。

## 10. 路线图（Go 唯一实现路径）

按依赖顺序排列，探测先行——它是产品核心价值，也是最大技术风险：

1. **`core` 探测原语**：overlay-diff + whiteout 收集 + 语义分类，拿真实 Electron
   应用跑通"探测 → 生成档案"闭环（[discover.md](discover.md) §3.2）；
2. **`core` 其余部分**：`BuildBwrapArgs` 纯函数 + 单测、档案 TOML 解析、实例 CRUD；
3. **CLI MVP**（cobra）：`add/run/list/rm/doctor`，命令面即本文 §6 表格；
4. **`cmd/appclone-gui`**：gotk4 + libadwaita 三屏（ADR-006：一版列表+开关，
   discover 勾选界面紧随其后——它是 GUI 的最大价值点）；
5. 桌面图标角标（Overlay Icon / 不同 Icon= 资源）区分分身；
6. `add --fork`：§8.1 的一键化（检测 fuse-overlayfs，自动 lower=主实例）；
7. 档案库社区化（类似 Firejail profile 的分发模式），经 GitHub Releases 分发。
