# Linux 应用分身（App Clone）方案设计

> 目标：在桌面 Linux 上实现类似 Android "应用分身 / Cloned Apps" 的功能——
> **只隔离目标应用自身的配置与数据**（两个实例互不可见、可同时运行），
> **其余一切照常共享**（下载、文档、剪贴板、通知、输入法、GPU/音频）。
> 无需 root，无需修改应用本身。

**文档体系与版本定位**

| 文档 | 内容 |
|---|---|
| 本文（方案设计） | 需求定义、隔离机制、目录布局、档案规范、验证清单——跨视图稳定的设计契约 |
| [tech-stack.md](tech-stack.md) | 技术选型与 ADR：引擎（bubblewrap）、实现（Go，唯一路径）、GUI（GTK4+libadwaita，puregotk 绑定） |
| [discover.md](discover.md) | 路径自动探测方案（ADR-008） |

实现形态：**Go 单仓库**（`core` + `cmd/appclone` CLI + `cmd/appclone-gui` GUI），
产品直达普通用户（GUI 为主入口，CLI 服务开发者）。本文定义的命令语义、
实例目录布局、档案字段语义是 CLI/GUI 双视图共同遵守的契约，与视图无关；
选型理由一律见 tech-stack.md。早期 bash 原型（`legacy/`）仅用于隔离语义验证，
不属于产品路径（ADR-002）。

## 1. 设计目标与非目标

**目标**

- 同一应用多个实例并行运行，各有独立账号/聊天记录/设置；
- 实例间私有数据互不可见（含内核层面的 mount 隔离）；
- 公共文件（`~/Downloads` 等）与会话资源全部共享——分身下载的文件直接出现在原位置；
- 对应用黑盒：不依赖应用支持多开参数；
- 一条命令创建/删除分身，并生成可直接打开的桌面入口（近似 Android 的"开关"体验）。
  v1 的区分手段是入口名称后缀「（分身 <显示名>）」——GNOME 无 Overlay Icon 机制，图标角标列为后续（§10 第 5 项）。

**非目标（当前版本不做）**

- 强权限隔离（分身进程拿不到主实例数据的访问权）——那是 user namespace + 独立 UID 的路线，复杂度高且引入桌面会话授权问题；
- Flatpak 应用内部分身（另有思路，见 §8.4）；
- Windows/Wayland 单显示会话外的多桌面环境。

## 2. 与 Android Cloned Apps 的机制对照

| Android（多用户机制） | 本方案（mount namespace） |
|---|---|
| `installExistingPackageAsUser(pkg, profileId)`，数据目录自动出现在 `/data/user/<id>/<pkg>/` | 档案 `paths` 字段 + `--bind 实例目录 原路径`，数据目录重定向到 `instances/<app>/<id>/root/` 下 |
| PMS 安装时**统一分配**数据目录（路径确定，所以一个开关即可） | Linux 无"户籍管理"，用 per-app **路径档案**事后补齐这份知识 |
| AMS 按 userId 检测单实例 | 私有 DBus 会话总线 + 锁文件 inode 替换 |
| Launcher 显示两个图标 | 自动生成 `.desktop`（Name 加「分身」后缀） |
| 克隆 profile **共享**父用户外部存储 `/storage/emulated/0` | `--bind / /` 整个根文件系统原样透传，天然共享 |

## 3. 总体架构

分身执行链（对两个版本一致）：

```
桌面入口  appclone-<app>-<id>.desktop
   │
   └─ appclone run <app> <id>            ← CLI 视图（GUI 是同一 core 的另一视图）
        ├─ core：加载档案  profiles.d/<app>.toml（路径知识库 = 事后补做的 Android PMS 安装期目录分配）
        ├─ core：构造 bwrap 参数（BuildBwrapArgs —— 项目的事实核心，纯函数，见 §3.1）
        │      --unshare-user --unshare-pid --unshare-ipc
        │      --bind / /                      ← 整个系统原样透传（其余全部可见）
        │      --dev-bind /dev /dev  --proc /proc   ← 必须在 --bind / / 之后（后绑定覆盖先绑定）
        │      --bind 实例私有目录 应用数据路径   ← 仅偷换应用自己的目录
        │      --bind 实例私有空文件 应用锁文件    ← 绕过 flock（仅普通文件锁，socket 见 §6.2）
        │      （可选）私有 DBus session bus
        │      （可选）私有 XDG_RUNTIME_DIR（wayland/pulse socket 仍共享进来）
        └─ exec bwrap ... -- <应用可执行文件>
```

**生命周期归 `appclone run`，不归 bwrap**：`--die-with-parent` 只保证直接子进程，
应用自己 `fork`+`setsid` 出来的进程会逃出这条链路（bwrap 0.13.1 实测）。
所以 `run` 不 `exec` bwrap，而是 `setsid` 起 bwrap、自己常驻为父进程，
在 bwrap 退出或自己收到 `SIGTERM`/`SIGINT`/`SIGHUP` 时对**整个进程组**发 `SIGTERM`，3 秒后 `SIGKILL`
（`--unshare-pid` 保证 bwrap 死则 namespace 内的 PID 1 死，内核连带清空）。
这段逻辑与探测期共用一份实现（[discover.md](discover.md) §3.2.3，决策见 [tech-stack.md](tech-stack.md) ADR-020），不写两遍。

**GUI 启动的分身与设置窗口解耦**（ADR-028）：GUI 点「启动」时不把 `core.Run` 跑在自己的进程里，
而是用自身二进制 fork 一个会话首进程（runner）执行同一条 `core.Run`。关掉设置窗口只会结束 GUI，
不会结束正在运行的分身；详情页在运行中提供「停止」，向 runner 发 `SIGTERM` 走同一套进程组终止链。
runner 是一次性进程，不监听、不提供 API——**不是 daemon，也不引入 IPC**（ADR-004 不变）。

**不做前后端分离**：无 daemon、无 IPC 协议。CLI（cobra，开发者视图）与 GUI
（puregotk → GTK4/libadwaita，普通用户主入口，见 tech-stack.md ADR-004/005/013）是同一 core 的两个薄视图，
GUI 崩溃不影响 CLI 功能完整性。

**核心原理一句话**：进入一个私有 mount namespace，在里面把整个文件系统原样 bind 进来，只把应用读写自身状态的那几个目录换成分身专用的副本。替换仅存在于该进程的命名空间内，主用户环境零影响，不需要 root。

### 3.1 bwrap 参数构造契约（`core.BuildBwrapArgs`）

这是项目的**事实核心**，参数集与顺序都是契约，缺一项或调错顺序就算实现错误。

**签名必须是可返回错误的纯函数**（原写法只返回 `[]string`，与"`core` 必须拒绝公共目录"自相矛盾——
实现者只能 panic、静默丢路径，或把校验挪到调用方，CLI/GUI 各写一份）：

```go
// 纯函数：不读环境变量、不探文件系统。存在性与权限由 PrepareBindTargets 前置完成（见 §3.2 第 2 条）。
func BuildBwrapArgs(p Profile, in Instance, o BuildOptions) ([]string, error)

type BuildOptions struct {
    Resolver     *PathResolver // 路径展开的唯一实现（§6.4）；纯函数靠它而不是读环境
    Base         string     // AC_BASE 绝对路径（判断 paths 是否踩到自己的运行时根）
    RealHome     string     // 真实 $HOME（宿主路径）
    Home         string     // 有效 HOME：AC_HOME 或 RealHome；所有 ~ / $HOME 按它展开（§6.4）
    UID          int
    RuntimeDir   string     // 宿主 XDG_RUNTIME_DIR
    RuntimeSocks []BindPair // 已探测存在的宿主 socket → 私有 runtime 内目标（只读，见 §6.2）
    DBusAddress  string     // dbus-daemon --print-address 的原文；空 = 不隔离
    XDG          map[string]string // XDG_CONFIG_HOME 等，供路径展开
}
type BindPair struct{ Src, Dst string }
```

非法输入（`paths` 含公共目录 / `/` / `$HOME` / `AC_BASE` / 父子重叠未归一 / `env` 含保留键 /
`extra_binds` 目标越界）返回 `*core.Error{Code:2}`，**不得 panic、不得静默丢路径**（§11）。

| 顺序 | 参数 | 必需 | 理由 / 失效后果 |
|---|---|---|---|
| ① `--unshare-user` | ✅ | 非特权 user namespace。**目标用户是普通账号，缺此项 bwrap 直接报 "No permissions to create new namespace"**（root 会话下反而能跑通——所以不能拿 root 环境验证通过当结论） |
| ② `--unshare-pid` `--unshare-ipc` | ✅ | 主实例与分身不共享 PID/IPC 视图；不隔离则 `pgrep` 归因失效，`--proc /proc` 也失去意义。**`--unshare-uts` 不用**（ADR-021） |
| ③ `--bind / /` | ✅ | 全透传，公共目录共享的根 |
| ④ `--dev-bind /dev /dev`、`--proc /proc` | ✅ | **必须排在 `--bind / /` 之后**：bwrap 同目标后挂载覆盖先挂载，写在前面等于被抹掉 |
| ⑤ `paths`：`--bind <inst>/root/<p> <p>` | ✅ | 仅 `paths` 声明的目录；**按深度升序**（父先子后），重叠项在 `ValidateProfile` 里已归一。**归一保留祖先是刻意的**：父目录已经覆盖子目录，保留子项只会多一条冗余 bind；反过来若只留子项，父目录的其余内容就留在共享层——那才是真正的漏隔离（原措辞"最具体项"与 bwrap 语义相反，已改）；公共 XDG 目录出现在此列表 → 拒绝（`core` 强制，不靠调用方自觉）。**实例侧源路径映射写死为 `filepath.Join(in.Root, strings.TrimPrefix(abs, "/"))`**：`/home/u/.config/App` → `<inst>/root/home/u/.config/App`，`/var/lib/app` → `<inst>/root/var/lib/app`。不许用 `filepath.Join(in.Root, abs)`（`Join` 遇到绝对路径会**丢弃前半段**，源直接指向宿主真实路径，隔离静默失效），映射后必须断言 `filepath.Clean(src)` 仍在 `in.Root` 之下，否则报 1（内部 bug）。**同深度按字典序**做 tie-break——没有全序的排序，`doctor` 打出来的命令两次不一致，golden 断言也无从写起 |
| ⑥ `shared_writes`：`--bind-try <real> <p>` | 可选 | **必须排在 ⑤ 之后**：`paths` 可能声明了父目录（如 `~/.config`），共享项要在它之上把真实文件盖回来，否则分身里输入法失效、书签消失（§5.4）。源不存在时用 `-try` 跳过（`recently-used.xbel` 首次运行可能没有） |
| ⑦ `extra_binds`：`--bind <src> <dst>` | 可选 | 源必须存在；目标不得是公共目录 / `$HOME` / `AC_BASE` / `instances/` 之下，也不得与 ⑤ 的目标重叠（重叠即档案自相矛盾，报 2）。**排在 ⑤⑥ 之后**：它是"档案里没有的补充"，盖在实例层之上才符合意图 |
| ⑧ `lock_files`：`--bind <inst>/locks/<hash>.lock <lockpath>` | 可选 | 仅普通文件锁；`hash = hex(sha256(cleanAbsTarget))[:16]`，文件名 `<hash>.lock`（**不要用数组下标**：档案顺序一变私有锁就换名，旧文件永久残留）。实例侧文件由 core 预建 0600。socket 见 §6.2 |
| ⑨ `isolate_runtime`：`--bind <inst>/runtime <XDG_RUNTIME_DIR>` + `--setenv XDG_RUNTIME_DIR <同一值>` | 条件 | **`--setenv` 不能漏**：只 bind 目录不改环境变量，应用仍按旧值找 socket。随后把宿主 socket **只读** bind 进新 runtime（顺序必须在目录 bind 之后，否则被覆盖）；清单见 §6.2 |
| ⑩ `isolate_dbus`：`--bind <inst>/dbus/bus <runtime>/bus` + `--setenv DBUS_SESSION_BUS_ADDRESS <地址>` | 条件 | 地址取 `dbus-daemon --print-address` 的**原文**，不许自己拼 `unix:path=`（§6.6）。**`isolate_dbus = true` 隐含 `isolate_runtime = true`**（`BuildBwrapArgs` 内部强制，档案不用写两项）：不隔离 runtime 时 `<runtime>` 是宿主 `$XDG_RUNTIME_DIR`，而 bwrap 会在**宿主**为不存在的 bind 目标建占位物（§3.2 第 2 条）——那个 `bus` 占位文件正好压住真实的 session bus socket，同一会话里所有应用的通知/输入法一起断，且这属于"工具写到白名单之外" |
| ⑪ `--setenv HOME <AC_HOME>` | `AC_HOME` 生效时 | **不做这一步，`AC_HOME` 只在工具自己的路径计算里生效，应用读到的仍是真实 `$HOME`**——隔离测试会假通过（§6.4） |
| ⑫ `--setenv VAR value` × `env`、`--chdir <cwd>` | 可选 | **保留键拒绝**：`HOME`、`XDG_*`、`DBUS_SESSION_BUS_ADDRESS` 由 core 产出，档案里出现即判非法（退出 2）。否则 `env = {HOME="..."}` 能让 ⑨⑪ 静默失效，正是 §6.4 说的"最危险假通过"。**`env` 按 key 字典序输出**（Go map 迭代顺序随机，不排序则同一条档案每次生成的命令都不同，`doctor` 输出无法 diff、golden 断言无法写）。**`cwd` 在宿主不存在时不报错**：bwrap 的 `--chdir` 到不存在的目录会让整条命令失败，而这是"应用升级删了工作目录"级别的偶然事件，不该让分身起不来——回退到有效 `HOME` 并在 stderr 留一行提示（GUI 无 stderr，故同时记进 `last_error` 供详情页展示） |
| ⑬ `--die-with-parent` | ✅（兜底） | **只保证直接子进程**；真正的生命周期由 `appclone run` 常驻父进程 + 进程组 kill 保证（§3 末段、§6.2） |

**一律不传的参数**：`--uid`/`--gid`/`--cap-add`/`--cap-drop`/`--seccomp`/`--new-session`。
默认最小集已满足需求；`--new-session` 由外层 `setsid` 承担（§3 末段），叠加会多一个变量。

**euid == 0 直接拒绝**（`run`/`add` 都拒，退出码 3）：root 会话下 `--bind / /` 是 rw，误操作能改宿主系统；
而且 root 下 bwrap 本来就能跑通，"验证通过"会把非特权路径的问题全部藏起来。

**单测必须覆盖**（golden 断言 argv 全序，不只是"包含某参数"）：`--dev-bind` 在 `--bind / /` 之后、
`shared_writes` 在 `paths` 之后、runtime socket 在 runtime 目录之后、`--setenv` 与对应 bind 成对出现、
公共目录被拒、`paths` 含 `/`/`$HOME` 被拒、`env` 含保留键被拒、`extra_binds` 与 paths 重叠被拒、
路径含空格/中文、`id` 含特殊字符、`isolate_dbus` 与 `isolate_runtime` 组合、`AC_HOME` 生效时必带 `--setenv HOME`。

### 3.2 三条 bwrap 行为依赖（2026-11-06 实测 bwrap 0.13.1）

这个方案压在 bwrap 的三个具体行为上。它们不是文档承诺，是**实测结论**——升级 bwrap 或改参数顺序前必须重验，
否则会静默失效。

| # | 实测行为 | 对方案的后果 |
|---|---|---|
| 1 | **`--bind` 的源按宿主根解析**，不受前面 bind 影响：`--bind A X` 之后再 `--bind X Y`，`Y` 看到的是 A 被 bind 之前的原始 X | 探测期"overlay 罩住 `$HOME`，再把真实公共目录 bind 回去"**成立**（否则源与目标是同一路径，摘出变成空操作，用户文件照样落 upper）。**必须加会话内正向断言**：探测会话里对每个公共目录确认看到的是真实目录（`findmnt -no SOURCE --target` 或写-读标记），不能只靠"计划上应该生效" |
| 2 | **bind 目标不存在时 bwrap 自己创建，而且创建发生在宿主**（`--bind / /` 是 rw）：目录 0755、文件 **0444** | (a) 0444 占位文件会让应用 `O_WRONLY` 打开失败，也会让**主实例之后打不开同名锁文件**——`lock_files` 的宿主目标必须由 core 预建 0600；(b) 那是"工具写到白名单之外"，所以 §4 白名单必须显式包含这条例外，并要求 `EnsureBindTarget` 记录本次新建清单、失败时回收 |
| 3 | **源不存在时 `--bind` 直接失败**（整个 `run` 起不来）；`--bind-try` 静默跳过 | 一切"可能不存在"的源用 `-try`（`shared_writes`、宿主 socket）；但 ⑤⑦⑧ 的**实例侧源必须存在**——不存在是 core 的 bug，不许用 `-try` 掩盖 |

## 4. 目录与文件布局

```
~/.local/share/appclone/          # 运行时根，可用 AC_BASE 覆盖（见 §6.4）
├── .lock                   # 全局写锁（flock）：所有写操作串行化，见 §4.2
├── profiles.d/
│   └── <app>.toml          # 应用档案：exec、paths、lock_files 等（见 §5）
├── instances/
│   └── <app>/<id>/
│       ├── instance.toml   # 实例元数据：display_name / created_at / probe_method
│       ├── root/<原路径>/  # 偷换后的数据目录（如 root/home/u/.config/WeChat/）
│       ├── locks/          # 私有锁文件（bind 到各 lock_files 路径）
│       ├── runtime/        # （可选）私有 XDG_RUNTIME_DIR
│       ├── dbus/           # （可选）私有 DBus 总线 socket
│       ├── .fork/          # （可选，fork 实例）运行期 overlay 的挂载点与工作区；卸载后可删，不在 root/ 内
│       ├── run.lock        # 运行态标记：run 期间持有 flock，见 §4.3
│       ├── run.pid         # 停止信号目标："pid starttime"，仅 stop 使用（ADR-028）
│       ├── run.log         # （可选）GUI 启动的 runner 输出，封顶 1 MiB，不是用户数据
│       └── audit/          # （可选）运行期审计的轻量证据：run.toml、summary.toml、quarantine-*/；写层在 /var/tmp（§4.4/§6.5）
├── probe/                  # 探测临时区：upper/（写入层）、work/、merged/、runtime/、dbus/，探测结束即删
├── cache/apps.toml         # .desktop 元数据缓存（带源文件 mtime 校验），损坏即重建，见 §6.1.1
└── ui.toml                 # GUI 自身偏好（窗口尺寸、上次选中项），损坏即重建默认值
~/.local/share/applications/
└── appclone-<app>-<id>.desktop   # 生成的桌面入口
```

程序对用户目录的写入点**枚举如下**（工具自身的写入白名单，多一处即 bug）：
`.lock`、`profiles.d/`、`instances/`、`cache/apps.toml`、`ui.toml`、`~/.local/share/applications/appclone-*.desktop`，
以及**必须自清理**的临时区：探测用的 `probe/`、fork 实例运行期的 `.fork/`（在实例目录内，见 §8.1）。
临时区在操作结束（含失败）时清空，残留即 bug——但 **`instances/<app>/<id>/root/` 是持久数据，永远不在清理范围内**。

**白名单的唯一显式例外：bind 目标的占位物**。`paths` / `lock_files` 的宿主目标在首次运行时可能不存在，
而 bwrap 会自己建（实测：目录 0755、文件 **0444**），且建在宿主上——0444 的占位文件会让应用 `O_WRONLY` 打开失败，
也会让主实例之后打不开同名锁文件。所以 `run`/`add` 必须先跑 `PrepareBindTargets`：
只为这两类目标补建目录 `0700` / 空文件 `0600`，**只增不删**，并记录"本次新建清单"（失败时回收自己建的那些）。
`shared_writes` 与宿主 socket 一律用 `--bind-try`，不存在就跳过，绝不代建（§3.2 第 2、3 条）。

**权限矩阵**（同机其他用户不该能看到分身数据）：

| 路径 | 权限 | 理由 |
|---|---|---|
| `AC_BASE`、`profiles.d/`、`instances/`、`<id>/`、`root/`、`locks/`、`runtime/`、`dbus/`、`audit/`、`.fork/` | `0700` | 分身数据含聊天记录级隐私；`.fork/` 里是挂载视图与 overlay 工作区，同样不能给别的用户看 |
| 档案 `*.toml`、`instance.toml`、`.lock`、`run.lock`、`run.pid`、`run.log`、私有锁文件、`summary.toml` | `0600` | 同上；锁文件必须可写（0600），不能是 0444；`run.log` 可能含应用输出，同样不能给同机其他用户读 |
| `probe`（临时区，见 §4.4）、`ui.toml`、`cache/apps.toml` | `0700` / `0600` | 临时区本身就含用户文件副本 |
| 生成的 `appclone-*.desktop` | `0644` | 桌面环境要能读 |

时间一律 RFC3339 UTC（`created_at`/`last_used_at`/`summary.toml` 的时间戳同一格式），不用本地时间。

`instances/<app>/<id>/audit/` **不在上面"必须自清理"之列**：它的生命周期由 `doctor --verify` 管理
（运行结束保留证据、verify 消费后只留摘要），见 §6.5。把它归进"临时区"会导致 verify 永远读不到证据——
这两类东西的寿命不同，别按同一张清单处理。

**别把两件事混成一件**：这份白名单约束的是**工具自身**写了什么；
而 `doctor --verify`（§6.5）判定的是**被分身的应用**有没有写到实例目录之外。对象不同，判定逻辑也不同。

**契约性质**：本布局是 CLI/GUI 双视图共用的事实标准——互操作优先于格式洁癖。

**三个名字的语义必须分清**（历史上这里混过，改代码前先对齐）：

| 名字 | 位置 | 是什么 | 谁写 |
|---|---|---|---|
| `profiles/<app>.toml` | **仓库内** | 内置档案模板库（随发行分发、可选、社区可贡献） | 开发者 |
| `profiles.d/<app>.toml` | `~/.local/share/appclone/` | 运行时档案，探测管线生成，实际生效的那份 | 程序 |
| `instances/<app>/<id>/` | 同上 | 分身数据 | 程序 |

运行时档案优先于内置模板；同名时以 `profiles.d/` 为准，内置模板仅作首次生成的预填来源。
**CLI 与 GUI 同一条规则**：`add` 的首次配置 / 重新配置 / 重新探测**一律真探测**（模板路径只补进
候选、模板的非路径字段只在没有既有档案时当基线），`--rediscover` 不得因为"有模板"跳过探测——
否则同一应用会由 CLI 落出 `manual` 档案、由 GUI 落出 `overlay` 档案，应用升级后也永远校正不了路径。

**`<id>` 规则**（删除路径会拼到它，必须有硬约束）：

- 合法字符集 `[a-z0-9][a-z0-9_-]{0,31}`，**拒绝 `.`/`..`/`/`/空格/非 ASCII**；
- **省略 id 时自动分配**：按 `main`、`inst2`、`inst3`… 取第一个空闲（用户说"再来一个分身"时不该被报错打断）；
- **显式指定 id 且已存在 → 报错**并列出已有 id，**不得静默覆盖、也不得偷偷追加序号**（用户明确说了要 `work`，给他 `work2` 是欺骗）；
- 两条的区别只在"用户是否指定"——这是唯一的判定依据；
- 校验在 `core` 里做一次权威实现，CLI 与 GUI 共用，不得各自写正则。

**`<app>` 规则**（同样会拼进路径，之前只定义了 `id` 是漏的）：

- 取值 = 源 `.desktop` 的文件名去 `.desktop` 后缀（desktop id 的 basename，不含目录），
  校验 `[a-z0-9][a-z0-9._-]{0,63}`，**显式拒绝** `.`、`..`、空串、含 `/`、前导 `.`、`appclone-` 前缀
  （前缀是分身入口的保留命名空间，§4.1）；不合规就拒绝该应用并记一条 `ScanError`，不进列表；
- **归一化不是"校验后丢弃"**：真实系统里存在 `CC Switch.desktop`、`WorkBuddy AI.desktop` 这种带空格的文件名
  （本机 `/usr/share/applications` 就有两个）。直接按字符集拒绝的后果是这些应用在列表里彻底消失、且没有任何提示。
  所以 `core.SanitizeAppKey` 先把非法字符换成 `-`（合并连续、去掉首尾的 `.`/`-`），归一化后仍不合规才拒绝。
  `ValidateAppKey` 只用于"用户显式输入/目录名"这类必须严格匹配的场景，扫描路径一律先过归一化；
- **名字归一化可能撞车**（`Foo.desktop` 与 `foo.desktop` 归一到同一个 key）：按来源优先级（用户级 > 系统级 > Flatpak）
  保留高优先级者，另一个在 key 尾部加稳定短哈希（`hex(sha256(源路径))[:6]`），映射关系写进 `cache/apps.toml`，
  保证同一台机器上每次扫描结果一致；
- 校验与 `id` 一样在 `core` 单一实现（`ValidateAppKey`），CLI 与 GUI 共用。

**实例元数据与显示名（`id` 与 `display_name` 是两件事，别混）**：

```toml
# instances/<app>/<id>/instance.toml —— 唯一权威的实例元数据（GUI/CLI 都读它，不读目录推断）
version      = 1                 # schema 版本，规则同档案（§5.5）
app          = "wechat"          # 冗余存一份，便于实例目录被单独移动时自证归属
id           = "work"
display_name = "工作号"          # 用户可见名，1..32 rune，NFC，禁控制字符/换行，应用内唯一（§4 显示名规则）
created_at   = 2026-11-06T12:00:00Z   # RFC3339 UTC
last_used_at = 2026-11-06T12:30:00Z   # 最近一次 run 开始时间；从未运行则省略
probe_method = "overlay"         # 创建时的档案来源快照；**权威值仍是 profiles.d 档案里的那份**
fork         = true              # （可选）克隆起步：run 时以主实例数据为只读 lower、root/ 为 upper（§8.1）
```

- `id`：目录名与删除路径的组成部分，硬约束见上，**只允许 ASCII 小写**；
- `display_name`：给用户看的名字，**可以中文、空格、emoji**，默认是「分身 N」（N = **最小未占用的正整数**），
  存在 `instance.toml`。**默认值不是 `id`**——`id` 是 `main`/`inst2` 这种机器名，让它出现在概览里
  就等于把内部标识摊给用户，与"用户永远不该看到 `work`"这条自相矛盾；
- 桌面入口的 `Name=` 用 `display_name`（`微信（分身 工作号）`），路径一律用 `id`（`instances/wechat/work/`）；
- GUI 的「重命名」改的是 `display_name`，**不碰 `id`**——改 id 等于搬目录，风险高且无收益；
  `id` 只在创建时分一次，此后不可变；
- **默认显示名取"第一个空闲的「分身 N」"**（扫描该应用全部 `instance.toml` 后取最小未占用 N），
  不是"实例数 + 1"：删掉中间那个实例后，`数量+1` 会撞上已有的「分身 2」，GNOME 里两个入口同名、无法区分；
- `display_name` 规则：trim 后 1..32 rune、NFC 归一、**拒绝控制字符与换行/制表符**（换行会截断 `.desktop` 的 `Name=` 行，
  生成一个损坏的入口）；**同一应用内唯一**（重命名撞名拒绝，退出 5），跨应用允许重名；
- `.desktop` 的 `Name` 因此在重命名后需要**原子重写同一个文件**（同目录 `tmp + fsync + rename`）。
  入口文件名是 `appclone-<app>-<id>.desktop`，只由 `app`/`id` 决定，**重命名不换文件名**——
  原文写的"删旧入口→trash 新建"是多余动作：会往回收站里堆过期入口，还会在删与建之间留一个"入口消失"的窗口。

**删除语义**：实例目录与桌面入口一律 `gio trash` 移入系统回收站，**不设私有 `.trash/` 目录**（私有 trash 没有清理策略，等于无限增长）。永久删除只在用户手动清空回收站时发生。

**可删范围是硬白名单**（`core` 里唯一实现 `trashable`，调用方不许各自拼判断）：`<AC_BASE>/instances/`、`<AC_BASE>/profiles.d/`（仅 `--purge-profile`）、`<数据目录>/applications/appclone-*.desktop`。越界路径**报 5 且不调用 `gio`**——`app`/`id` 由用户输入拼进路径，漏一处校验就是把 `AC_BASE` 之外的目录交给回收站（与 §6.3 的 5 同一口径）。目标已不存在不算错误（并发两次删除、用户先在文件管理器删掉，都只是"它已经不在了"）。

### 4.1 生成的桌面入口规范

分身入口是用户在 GNOME 概览里唯一会看到的东西，字段必须一次写对——少一个 `Type=` 或 `Exec=` 引号错，图标就消失或点了没反应。

```ini
[Desktop Entry]
Version=1.0
Type=Application
Name=微信（分身 工作号）
Name[zh_CN]=微信（分身 工作号）
Name[en]=WeChat (Clone · 工作号)
Exec=/home/u/.local/bin/appclone run wechat work %U
TryExec=/home/u/.local/bin/appclone
Icon=com.tencent.wechat
Terminal=false
StartupNotify=true
StartupWMClass=wechat
Categories=Network;InstantMessaging;
X-Appclone-App=wechat
X-Appclone-Id=work
```

规则：

- **源字段取自被分身应用的 `.desktop`，不猜**：`Icon`、`StartupWMClass`、`Categories` 原样继承（`StartupWMClass` 缺省则整行省略，不写空值）；
- **继承是白名单，不是"抄一遍"**：只继承上面三个键（必要时加 `Keywords`）。`Actions`/`MimeType`/`DBusActivatable`
  **必须丢弃**——继承它们会让分身重复注册 MIME 处理与 DBus 名，右键菜单和文件关联直接错乱；
  写值时统一过 `escapeDesktopValue`（`\`、换行、制表符转义）与 `quoteExecArg`，否则第三方 `Name=` 里的换行
  能把后续任意键注入进来；`Version=1.0` 固定写（这是 Desktop Entry 规范版本，与被分身应用的版本无关）；
- **`Name` 必须带「（分身 <display_name>）」后缀**：GNOME 没有 Overlay Icon 机制，这是用户区分主实例与分身的第一视觉线索（[tech-stack.md](tech-stack.md) §4.8）。
  **后缀里放显示名，不是 `id`**——`id` 只出现在目录路径与 `X-Appclone-Id=` 里，用户永远不该看到 `work` 这种名字；
- **`Name` 有长度上限（40 rune，含后缀）**：GNOME 概览标签在小图标下约 12 个全角字符后截断，
  超长显示名会让两个分身看起来一模一样（后缀被切掉）。超限时截断 `display_name` 部分并补 `…`，
  同时 `display_name` 本身在 `core` 里限制 32 rune（与 `id` 的 32 对齐），两处上限各有各的理由，别只留一个；
- **本地化只翻模板，不翻用户数据**：`Name[zh_CN]`/`Name[en]` 由 i18n 消息表拼出（`clone_name_suffix`），
  `display_name` 原样嵌入不翻译。`.desktop` 的 `Name=` 无 `[lang]` 时作为兜底，必须写；
- **`Exec` 必须写解析后的绝对路径，而且必须是 CLI 二进制的路径**，**不能写裸 `appclone`**：
  图形会话的 PATH 不保证包含 `~/.local/bin`，裸命令的后果是"图标点了没反应"这种最难查的故障。
  **不能用 `os.Executable()`**——生成入口的调用者通常是 `appclone-gui`，照抄会把入口写成
  `appclone-gui run ...`，点击只会再弹一个设置窗口（`GtkApplication` 还会把参数当自己的启动参数吞掉）。
  解析顺序固定为：同目录 sibling `appclone` → 构建期 `-ldflags -X` 注入的 CLI 路径 → `PATH` 查找；
  三者都失败就**拒绝生成入口并报错**（退出码 2），绝不回退到 GUI 二进制。
  `TryExec` 写同一个绝对路径，桌面环境据此把失效入口灰掉；
- **`Exec` 里的字段码要保留**：生成入口时保留源 `Exec=... %U` 的 `%U`/`%F`（文件管理器"用分身打开"依赖它）；
  源 `Exec` 没有字段码时**不要自己补**（补了会让应用收到它不认识的参数）；
  而**解析成档案 `exec` 字段时必须剥掉字段码**（见 §5 字段表）——两处语义相反，别混；
- **字段缺省值**（源 `.desktop` 缺该键时，不许留空、不许省略整行，否则图标空白或分类丢失）：
  `Icon` → `application-x-executable`；`Categories` → `Utility;`；`StartupNotify` → `true`；`Terminal` → **强制 `false`**（分身不启终端）；
- `appclone-` 前缀是硬约定：应用列表扫描时按此前缀排除自己生成的入口，否则会把分身当应用再分身；
- 分身入口**不进 `NoDisplay`**（它就是要出现在概览里）。

### 4.2 状态一致性（CLI 与 GUI 会同时操作同一个 `AC_BASE`）

单机也要按多进程处理：桌面入口、GUI、用户手敲的 CLI 完全可能同时动作。三条硬规则，`core` 里单一实现
（决策见 [tech-stack.md](tech-stack.md) ADR-022）：

| 规则 | 做法 | 违反的后果 |
|---|---|---|
| **写操作串行化** | `core.OpenState()` 打开 `AC_BASE/.lock` 并 `flock(LOCK_EX)`；`add`/`rm`/重命名/写档案/探测全程持有；等锁超时 5 秒报错（退出码 6） | 两个进程同时写 `profiles.d/<app>.toml`，后者截断前者的半份内容 |
| **文件原子替换** | 所有 TOML 写入 = 同目录 `.<name>.tmp.<pid>` → `f.Sync()` → `os.Rename` | 断电或崩溃留下半截档案，下次解析失败，用户看到"档案损坏" |
| **创建即判重** | 用 `os.Mkdir(instances/<app>/<id>)` 的 `EEXIST` 作为唯一判重依据，**不在锁外先 `stat` 再 `Mkdir`** | TOCTOU：两个进程都看到"不存在"，都创建，其中一个的数据被覆盖 |

**`.lock` 的作用域要收窄**（原写法"所有写操作持锁"会自锁）：它只保护**命名空间变更**——
`profiles.d/`、`instances/`、`~/.local/share/applications/appclone-*.desktop`。
`ui.toml`（GUI 拖窗口就写）、`cache/apps.toml`（启动扫描就写）**不持全局锁**，只做 `tmp+rename` 原子替换，
最后写入者胜出——否则 GUI 一拖窗口就把 CLI 的 `add` 卡到 5 秒超时报 6。
`run` 只在**自己实例目录内**写（`runtime/`、`dbus/`、`audit/`），由 `run.lock` 保护，不碰全局锁。

`core.OpenState` 的契约：`OpenState(ctx context.Context, timeout time.Duration) (*State, error)`；
进程内先过 `sync.Mutex` 再 `flock`（GUI 的探测 goroutine 与列表刷新在同一进程里各开一次会自锁）；
`Close()` 幂等；目录 0700、锁文件 0600；**只读命令（`list`/`doctor`）不持锁**。

`rm` 的原子性（原文只写"持锁重读"，不够）：检查"没在跑"与 `gio trash` 之间存在竞态——另一个进程可以在这中间
`run` 起来，随后整个实例目录被搬进回收站。所以 `rm` **自己以 `LOCK_EX|LOCK_NB` 打开并持有 `run.lock`
直到 `gio trash` 返回**；拿不到即退出 7（与"运行中的实例"同一判定）。关闭开关要删多个实例时，
先按固定顺序（app 名、id 字典序）逐个 `LOCK_NB` 拿锁，**任一个拿不到就整体放弃并释放已拿的锁**——
不许删一半。

### 4.3 运行状态判定（`run.lock`）

「这个分身是不是在跑」不能靠 `pgrep`（同名的主实例进程会让判定永远为真），也不能靠记 PID 文件（崩溃后残留假阳性）。
用**内核持有的文件锁**（决策见 [tech-stack.md](tech-stack.md) ADR-023）：

- `appclone run` 启动时打开 `instances/<app>/<id>/run.lock` 并 `flock(LOCK_EX)`，进程退出（含崩溃、被 kill）时锁由内核自动释放；
- `run` 自己**必须用 `LOCK_EX|LOCK_NB`**：拿不到立刻退出 7（"该分身已在运行"），**不许阻塞**——
  桌面图标被点两次是常态，阻塞的后果是"点了没反应"再叠加一个永远不返回的进程；
  想要等待语义得显式加 `--wait`（默认不等待）。**不做参数转发**：本项目没有 daemon/IPC，第二个 `run` 没有可转发的对象；
- 判定 = `flock(LOCK_EX|LOCK_NB)` 试探：拿到 = 没在跑（立刻释放）；拿不到 = 正在跑。**运行态判定不读 PID 文件**，没有 stale 假阳性；
- `run.pid`（`pid` + `/proc/<pid>/stat` 启动时刻）只是**停止信号的目标记录**（ADR-028）：`run` 拿到锁后写入、退出前删除；`stop` 先用 `run.lock` 证明实例确实在跑，再用启动时刻防 PID 复用，锁拿得到时把残留文件当 stale 清掉。它不参与"是否在跑"的判断；
- GUI 详情页的「运行中」标记、以及"关闭开关时提示还有实例在运行"都读 `run.lock` 这一个事实；
- GUI 启动的 runner 把应用 stdout/stderr 追加到 `run.log`（每次启动最多落前 1 MiB，超限静默丢弃），
  它只用于启动失败时给用户一句原因，不是日志产品、不做轮转；内容可能含应用输出，权限 0600，
  随实例目录一起进回收站即可；
- 这三个文件**不属于实例数据**：`rm` 时随实例目录一起进回收站无妨；除 `run.log`
  可能含应用输出（0600，随实例目录回收）外，其余文件不含用户内容。

### 4.4 探测与审计的写层位置（overlay 的 upper 绝对不能躺在 lower 里面）

实测（2026-11-06）：`upperdir` 位于 `lowerdir` 之内时，overlay **挂载不报错**，但视图立刻递归——
`ls merged/<更深层路径>` 直接 `ELOOP (Too many levels of symbolic links)`，`rm -rf` 也删不掉。
而默认布局 `AC_BASE = ~/.local/share/appclone` 正好在 `$HOME` 之内，探测的 lower 就是 `$HOME`：
不加约束的话，**默认安装的第一次探测就踩这个坑**，而且残留在盘上清不掉。

| 对象 | 位置 | 为什么 |
|---|---|---|
| 探测写层（`upper/` `work/` `merged/` `runtime/` `dbus/`） | `/var/tmp/appclone/probe.<uid>.<rand>/`（`MkdirTemp` 唯一目录，0700） | 必须在 `$HOME` 之外，也必须在 `AC_BASE` 之外（否则 upper 在 lower 里） |
| 审计写层（`upper/` `work/` `merged/`） | `/var/tmp/appclone/audit.<uid>/<app>.<id>/` | 同上，lower 是 `$HOME`（§6.5） |
| 审计证据元数据（`run.toml`/`summary.toml`/`quarantine-*/`） | `instances/<app>/<id>/audit/` | 跟着实例一起进回收站；`quarantine-*` 里可能装着用户文件，**永不自动删** |

**挂载前三段断言**（缺一不挂，报环境错误 3）：`realpath(upper)` 不是 `realpath(lower)` 的前缀；
`workdir` 与 `upperdir` 同一文件系统；`upper`/`work`/`merged` 三个目录都是空的（上一轮残留 → 先清理，清不掉就报错）。

**为什么不用 `$XDG_RUNTIME_DIR`**：它是 tmpfs，容量按内存算；探测会话里应用写的 `~/.cache` 全落这一层，
Electron 系很容易上 GB，ENOSPC 会让探测半途失败且理由难懂。`/var/tmp` 在磁盘上，容量语义与用户预期一致。

**`/var/tmp` 不随重启清空**，所以崩溃残留必须由下次启动清理：`add` / `run --audit` 开始时扫描
`/var/tmp/appclone/` 下属于本 uid 的目录 → 读 `/proc/self/mountinfo` 判断是否仍被挂载 → 是则 `fusermount3 -uz`
→ **删除前先跑反向断言（§6.5）**：那里面可能有用户文件，命中即保留现场并报错，不许直接删。

## 5. 应用档案（per-app 路径知识库）规范

这是整套方案中唯一需要人工维护的东西，也是 Linux 与 Android 架构差异的落点（Android 由系统在安装期统一分配目录，Linux 需要事后摸清）。

| 字段 | 说明 |
|---|---|
| `version` | 档案 schema 版本（整数，当前 `1`）。升级时按版本迁移，不猜字段 |
| `exec` | 应用可执行文件路径（必填，由 `.desktop` 的 `Exec=` 解析；必须剥掉 `%U`/`%F`/`%f` 等字段码、去掉 `env VAR=x` 前缀，裸命令用 `exec.LookPath` 解析成绝对路径，仍非绝对路径则档案无效） |
| `exec_args` | 启动参数**数组**（可选）。真实 `.desktop` 的 `Exec=` 常带固定参数（`--user-data-dir=…`、`sh -c …`），
Flatpak 应用是 `exec = "/usr/bin/flatpak"` + `exec_args = ["run", "org.example.App"]`。
只留一个字符串字段会把这些参数丢掉，应用等于起不来；`BuildBwrapArgs` 之后 `run` 直接 `exec(exec, exec_args...)` |
| `paths` | 需要隔离的目录列表（探测结果填入）。**存储形式与校验**：优先存 `~/...` 形式（跨机器可移植，运行时按有效 `HOME` 展开，§6.4）；XDG 变量指向别处时存绝对路径。
加载时必须过 `ValidateProfile`：`Clean` + `EvalSymlinks` 成真实路径、必须绝对、拒绝 `..`；
**拒绝 `/`、`$HOME`、`~/.config`、`~/.local/share`、`~/.local/state`、`AC_BASE` 及公共 XDG 目录本身与它们的祖先**。
两处"之下"也必须一起拒（原写法只挡了本身与祖先，恰好漏掉最危险的两个方向）：
① **公共目录之下的任何路径**——`~/Downloads/work` 会被隔离成实例私有，而第一原则是公共目录强制共享，
两个分身各存一份"下载"正是用户最不能接受的失误；② **`AC_BASE` 之下的任何路径**——把分身自己的运行时根
写进 `paths` 会让 `--bind` 自指（`instances/<app>/<id>/root/...` 变成它自己的子目录），且探测期 upper 在
`/var/tmp` 之外多一处自指风险。判定一律在 `EvalSymlinks` **之后**做（软链指向公共目录同样算命中）。
重复项去重、父子重叠**归一到最上层项并告警**；`paths` 为空 ⇒ 档案不可创建（§6.3） |
| `shared_writes` | 共享但可写的路径（见 §5.4）。不隔离，仅用于界面提示与 `doctor --verify` 的白名单 |
| `lock_files` | **仅普通文件锁**（`flock`/`O_CREAT` 的固定文件路径），运行时被替换为实例私有空文件 |
| `sockets` | 单例 unix socket 路径（如 `$XDG_RUNTIME_DIR/app.sock`）。**不能靠 bind 空文件处理**：普通文件盖在 socket 路径上，应用 `connect()` 直接 `ENOTSOCK` 起不来。这项只作为 `isolate_runtime` 的输入依据与排障提示 |
| `extra_binds` | 额外 bind，格式 `"源|目标"`，用于 `/var`、`/opt` 下写死的路径 |
| `isolate_dbus` | true = 私有 DBus 会话总线，绕过 well-known name 单例检测 |
| `isolate_runtime` | true = 私有 XDG_RUNTIME_DIR（wayland/pulse/bus socket 仍 bind 进来），**这是 socket 型单例的唯一正解** |
| `env` | 额外环境变量，`"VAR" = "value"`。**保留键拒绝**：`HOME`、`XDG_*`、`DBUS_SESSION_BUS_ADDRESS`（由 core 产出，档案里出现即判非法，退出 2），否则隔离变量可被档案静默覆盖（§3.1 ⑫） |
| `cwd` | 启动工作目录 |
| `probe_method` | 档案来源与证据强度：`overlay` / `strace` / `manual`（含内置模板预填）。决定重跑提示与 GUI 上的置信度标注 |
| `audit` | `true` = 每次运行都开运行期审计层（§6.5），用于"改路径频繁"的应用；默认 `false`（有性能代价） |
| `unsupported` | **不可隔离项清单**（`[{kind, path?, reason}]`）。keyring/Secret Service 这类"根本不在文件路径上"的东西进这里，
**不进 `paths`、不进 `shared_writes`**（后者是 `verify` 的"预期共享"白名单，混进去会让对账口径失真）。
非空时 GUI 详情页只读展示"这一项隔离不了"，CLI `doctor` 打印；它不影响 `paths` 的合法性判断 |
| `ignored` | 审计对账时的**预期噪声**（默认 `~/.cache`、`~/.thumbnails`、`~/.local/share/Trash`、`~/.local/state`）。
L2 规则明确 cache 不隔离，但正常应用启动就会写 `~/.cache`：不给忽略集的话，`--audit` 在真实应用上**必然**误报 `leak-detected`，
`verify` 的结论直接失去意义。审计输出必须列出被忽略的类别，不许悄悄忽略 |

### 5.1 档案示例：通用 Electron 应用模板（`~/.local/share/appclone/profiles.d/someapp.toml`）

```toml
exec = "/usr/bin/some-electron-app"
paths = [
  "~/.config/SomeApp",
  "~/.local/share/SomeApp",   # 部分应用还写 ~/.SomeApp，以探测结果为准
]
lock_files = ["$XDG_RUNTIME_DIR/SomeApp.lock"]  # 仅 flock 型锁文件
sockets = ["$XDG_RUNTIME_DIR/SomeApp.sock"]     # 单例 socket：靠 isolate_runtime 解，不 bind 空文件
isolate_dbus = true    # 若应用在 DBus 上抢 well-known name
isolate_runtime = true # socket 型单例必须开
env = {}
cwd = "~"
```

### 5.2 官方自带多开参数的应用（推荐直接用，不必上沙箱）

```bash
# Chromium 系（含各 Electron 应用）
chromium --user-data-dir="$HOME/appclone/instance2"

# Firefox
firefox -P profile2 -no-remote
```

对这类应用，XDG/专有参数方案比沙箱更干净；appclone 的档案机制留作兜底。

### 5.3 档案格式与生成

- 格式为 TOML（运行时落 `~/.local/share/appclone/profiles.d/<app>.toml`，仓库内 `profiles/` 只是内置模板库，语义见 §4），schema 带 `version` 字段；
- 档案**由探测管线自动生成**（见 [discover.md](discover.md) 三层管线），
  用户只在 GUI 勾选界面确认预判结果，**不要求用户手写任何档案字段**；
- 实例目录布局（§4）不随档案格式变化——升级后既有分身数据原地可用。

### 5.4 共享可写文件（不在 `paths` 里，但会互相污染）

有一类路径两实例都会写、又不该整体隔离（隔了功能就断）。它们不进 `paths`，但必须被识别并写进档案的 `shared_writes`，用于两件事：GUI 上的风险提示、以及 `doctor --verify` 的"预期共享"白名单（否则会被误报成隔离泄漏）。

| 类别 | 典型路径 | 处理 |
|---|---|---|
| GTK 最近使用 | `~/.local/share/recently-used.xbel` | 共享，接受两实例互相追加（GUI 提示"最近文件列表会混"） |
| GTK 书签 | `~/.config/gtk-3.0/bookmarks` | 共享 |
| 密钥环 / Secret Service | 系统 keyring（DBus 服务） | **共享且无法隔离**：两实例共用同一把钥匙。命中即标 `unsupported` 原因，见 §9 |
| 输入法状态 | `~/.config/fcitx5`、ibus 相关 | 共享（隔离会导致输入法不可用） |
| 剪贴板 / 通知 | DBus 服务 | 共享（这是产品语义：桌面资源照常共享） |

判断口径：**能被隔离且隔离后功能不坏的才进 `paths`；隔离后会坏的，一律进 `shared_writes` 并在界面上说清代价。** 不允许"隔离了但应用半残"这种中间态。

**一个例外要单独记**：密钥环那类"根本不在文件路径上"的东西（DBus 服务持有状态）**不进 `shared_writes`**，
而是标 `unsupported`。理由是 `shared_writes` 是"预期共享"的白名单，进去就等于告诉 `doctor --verify`
"这是正常的共享写入"；而 keyring 的问题不是共享写入，是**它压根没法被这个方案隔离**——两回事，混了会让校验口径失真。

### 5.5 档案 schema 版本策略（不写清就会出现"新版写、旧版读"的静默错解）

`version` 是整数，当前 `1`。规则按"读到什么版本"分三种情况，**没有第四种**：

| 读到的 version | 行为 | 理由 |
|---|---|---|
| `== 1`（当前） | 直接解析 | — |
| `< 1`（不存在） | 按 v1 迁移函数链逐级升级（v1 是首版，暂无迁移器）；解析失败即报错，不猜 | 迁移必须是显式代码，不是"缺字段就填默认值"的巧合 |
| `> 1`（来自更新的版本） | **拒绝加载并提示"档案由更新版本的 appclone 生成"**，退出码 2 | 猜新字段语义 = 用旧代码解释新数据，最坏情况是把该隔离的路径漏掉 |

四条配套约定：

- **未知字段保留**：解析用"已知字段映射 + 原始键值表"，重写档案时把不认识的键原样写回。
  否则用旧版改一次显示名就会把新版的字段抹掉；
- **缺字段用默认值，非法值报错**（两者不能混）：`isolate_dbus` 缺失 → `false`；
  `paths` 里出现公共目录 → **报错并拒绝加载**（不是"忽略这一条"）。
  默认值只处理"没写"，报错只处理"写错了"。
- **"拒绝加载"的落点是 `ValidateProfile`，不是 `LoadProfile`**：`LoadProfile` 只做 schema 解析与
  版本判定（它必须能把一份"路径已失效的档案"读出来给用户看，否则界面只能显示"档案损坏"），
  语义校验（`paths` 危险路径、父子归一、公共目录、受保护目录、`env` 保留键）统一由 `ValidateProfile` 承担。
  `ProfileState` 把两者串起来给出 `hasProfile`/`creatable`——**GUI 与 CLI 都只认它，不许自己拼**。
- **`ignored = []` 与"没写 `ignored`"是两件事，且必须原样往返**：前者是用户显式关掉默认噪声白名单
  （审计对账时什么都不忽略），后者才是"没声明、用默认表"。落盘格式化**不能**用 `omitempty` 把空表
  折成不写——那样 `save`→`load` 一次就变回 nil，重新探测会把用户的显式配置静默换成默认值。
  v1 的线格式用指针字段区分 nil 与空表（`ignored = []` 必须真的写出来）。

档案格式与实例目录布局解耦：档案升级不影响 `instances/<app>/<id>/root/` 的任何内容，分身数据原地可用。

## 6. 工具：appclone

产品入口是 GUI（`appclone-gui`，普通用户主入口）；CLI（cobra）服务开发者
与脚本化场景，两者共享 `core`，命令语义一致。**产品安装路径只有发行版包**（用户零门槛）：

```bash
sudo apt install ./appclone_1.0.0_amd64.deb          # Ubuntu 24.04+ / Debian 13+（arm64 机器换成 _arm64.deb）
sudo dnf install ./appclone-1.0.0-1.x86_64.rpm       # Fedora 41+ / CentOS Stream 10（arm64 是 .aarch64.rpm）
sudo pacman -U appclone-1.0.0-1-x86_64.pkg.tar.zst   # Arch / Manjaro（仅 x86_64）
```

**两个架构都出包**（amd64 + arm64，见 [tech-stack.md](tech-stack.md) §6）。Arch 的 arm64 是唯一例外：
Arch Linux ARM 是独立项目、AUR 的 `appclone-bin` 只装 x86_64 预编译，arm64 用户走 AUR 源码包 `appclone`
或 `.tar.gz`。

（开发者从源码试用 CLI 时才手工拷贝 `install -Dm755 appclone ~/.local/bin/appclone`——只装 CLI，
不含 GUI、桌面入口与依赖声明，不构成产品安装路径。）

依赖：`bubblewrap`（必需）；`libgtk-4-1 (>= 4.14)` + `libadwaita-1-0 (>= 1.5)`（GUI 必需，CLI 不需要）;
`fuse-overlayfs`（强烈推荐：缺它主探测降级 strace，只影响探测质量、不影响运行）；`strace`、`dbus`、`gio`（可选）。
各发行版的包名对应与打包细节见 [tech-stack.md](tech-stack.md) §6。

**一个必须写清的平台前提**：bwrap 依赖非特权 user namespace。Ubuntu 23.10 起默认
`kernel.apparmor_restrict_unprivileged_userns=1`，且 **Ubuntu 的 bubblewrap 包不带 AppArmor profile**，
所以裸装 bwrap 会报 `bwrap: setting up uid map: Permission denied`——这**不是** `unprivileged_userns_clone`
那个旧开关的问题，改它无效。由包安装脚本检测后写入 `/etc/apparmor.d/bwrap`（`userns,` 规则）并 reload，
用户零参与；发行版已提供该文件时跳过。细节见 [tech-stack.md](tech-stack.md) §6。

前提齐备由**发行版包的依赖声明**保证（这是产品路径，用户零参与）；GUI 缺库时无法自救（技术原因见
[tech-stack.md](tech-stack.md) §4.4），所以 `appclone doctor` 的定位是**开发者与支持场景的排障口**，
不是"让用户先开终端自查"——那违反用户零门槛红线。

**应用来源（一处都不能少）**：应用列表与 `add` 的候选集必须同时扫下列目录，用户级同名覆盖系统级：

| 目录 | 实测规模（2026-11-06 本机） | 说明 |
|---|---|---|
| `/usr/share/applications` | **397 个 .desktop** | 系统安装应用的主体，**只扫用户级会漏掉 97%** |
| `~/.local/share/applications` | 12 个 .desktop | 用户级与 appclone 自己生成的入口（生成的要排除，否则会把分身当应用再分身） |
| `/var/lib/flatpak/exports/share/applications`（存在时） | 本机不存在 | Flatpak 导出的应用 |

命令语义（CLI 名称与 GUI 操作一一对应，均由 core 承载）：

| 命令 / GUI 操作 | 作用 |
|---|---|
| `appclone add <app> [id]` / 列表页开关 | **默认语义 = 有合法档案就复用、跳过探测；没有才探测**（对应 GUI 的「开启分身」与「首次配置」两个入口——CLI 与 GUI 不能是两套语义）。`--rediscover` 强制重跑探测（对应「重新探测」）；`--profile-only` 只更新档案、不建实例；`--fork` 让新实例从主实例现有数据克隆起步（写时复制，见 §8.1，不能与 `--profile-only` 同用）。**创建前必须过 `ValidateCreatable`：`paths` 为空 ⇒ 拒绝（退出 2）**，否则 CLI 能造出 GUI 明确挡住的空档案，契约被撕开。`id` 规则见 §4 |
| `appclone run <app> <id> [--audit] [--wait] [-- args...]` / 详情页「启动」 | 在分身环境中启动；`run` **不 exec**，常驻为父进程持有进程组与 `run.lock`（§3 末段、§4.3）。**语法边界写死**：`--` 之前是 appclone 的 flag，`--` 之后**原样透传**给应用（`%U` 展开的 URI、以 `-` 开头的应用参数都靠它）；不带 `--` 时第一个非 flag 参数之后的全部算应用参数。`--audit` 开运行期审计层（§6.5）。**同一实例第二次 `run` 立刻退出 7，不阻塞**；`--wait` 才等待 |
| `appclone stop <app> <id>` / 详情页「停止」 | 停止正在运行的分身：先 `run.lock` 证明在跑，再按 `run.pid` 向 `run` 进程发 `SIGTERM`，由 `run` 对应用进程组 `SIGTERM`→3s→`SIGKILL`（§3 末段）。没有在跑 ⇒ 退出 7；`run.lock` 被占但 `run.pid` 缺失/对不上（正在启动、旧版本启动、或 verify 正持锁）⇒ 退出 7 并说明，**绝不盲杀 PID**。GUI 的「停止」与它是同一实现 |
| `appclone list [app] [--json]` / 列表页 | 列出应用与实例（应用来自 §6 上方三个目录 **∪ 有档案的 app ∪ 有实例的 app**——应用卸载后孤儿实例必须还能被看见和删除）。默认人类可读表格，**默认只列"配过或建过"的应用**（397 个从没碰过的应用全列出来是倾倒），`--all` 列全量；`--json` 给脚本用（schema 见 §11） |
| `appclone doctor [<app> [<id>]] [--json] [--strict]` | 环境检查（bwrap / userns / **AppArmor `apparmor_restrict_unprivileged_userns` 与 `/etc/apparmor.d/bwrap`** / fuse 三件套 / `dbus-daemon` / `gio` / **GTK4 与 libadwaita 版本**）+ 带参时打印将执行的 bwrap 命令（**排障用，只读**）。**退出码约定**：报告完成即 0（结论在输出里），参数错误 2，只有 `--strict` 才在必需项失败时返回 3——否则脚本无法区分"doctor 自己失败"和"检查结论是环境坏"。**GTK 版本必须用独立 helper 的 dlopen 探测，CLI 二进制绝不 import GUI 包**（否则纯 CLI 机器会在 init 阶段 panic）。**现状（2026-11）**：探测顺序为 `pkg-config --modversion`（有开发包时精确）→ 库文件名的 libtool 版本段（GTK 的 `libgtk-4.so.1.<minor*100>.<micro>`，如 4.24.1 → `…2400.1`）→ **`warn` + 明说"无法判定版本"**；三档都不冒充通过。libadwaita 在多数发行版上是平 soname（`libadwaita-1.so.0`），文件名给不出版本，此时只报"无法判定"而不是猜一个数。真正的 dlopen 探测（`gtk_get_minor_version()`，经 purego 免 cgo）随 GUI 增量落地——现在为它单引一个模块不划算，而"不知道"比"猜出来的版本"诚实 |
| `appclone doctor --verify <app> <id> [--json]` | **隔离校验**：只在**有审计证据**时给结论（§6.5）。三种输出：`verified` / `leak-detected`（列出越界路径）/ `unverified`（**没有审计层，无法归因**——不是"没问题"）。**`unverified` 不得显示为绿色/通过**。判定逻辑与证据处置都已实现（`core/verify.go`：六种证据情形 + `finalize` 按结论消费/隔离/保留）。**证据生产者已落地**（`run --audit`，2026-11-07）：overlay 写层在 `/var/tmp/appclone/audit.<uid>/<app>.<id>/`，开始即写"进行中"的 `audit/run.toml`、结束后补成含本次实际 bind 清单的完成凭证；上一轮现场未消费时**先搬进唯一命名的 `quarantine-*`** 再开始（不阻塞新审计，也不覆盖旧证据）。`verify` 先 `LOCK_NB` 拿 `run.lock`，拿不到就报"实例在运行"（退出 7）；判完写 `summary.toml` 并处置证据 |
| `appclone rm <app> <id>` / 详情页「删除」 | 实例 + 桌面入口一并 `gio trash`。运行中先拒绝（退出 7）。**只删实例与入口，永不删档案**——删了档案，GUI 的"配过但关掉"状态就消失，用户得重跑探测。要清档案用显式 `--purge-profile` |
| `appclone repair-desktop [<app>]` | 重建失效的 `appclone-*.desktop`（appclone 升级/搬家后 `TryExec` 指向旧路径，表现是"图标点了没反应"）。启动时若检测到不一致，GUI 用降级横幅提示、CLI 提示一条命令 |

**通用约定**：所有命令支持 `--json`，成功与失败都输出同一外形（`{ok, data}` / `{ok:false, error:{code,key,message,args}}`）；
错误一律带稳定的 `key`（i18n 消息键，§11），脚本按 `code` 与 `key` 分支，**不许解析人类文案**。
`args` 是对象，值的类型由字段语义决定：单值字段是字符串，**路径集合字段（如探测的公共目录、
污染清单）是字符串数组**——脚本请按 `key` 分支并对 `args` 做类型判断，不要假设所有 `path` 都是标量。

**`add` 与五个 GUI 入口的对应关系（写死，不许 CLI 与 GUI 各一套语义）**：

| 命令 | 档案状态 | 等价 GUI 入口 | 建实例 |
|---|---|---|---|
| `add <app>` | 无档案 | 首次配置（setup） | 建 |
| `add <app>` | 档案失效（`!creatable`） | 重新配置（reconfig） | 建 |
| `add <app>` | 档案可用 | 开启分身（open） | 建 |
| `add <app> <id>`（`<id>` 未被占用） | 档案可用 | 新建分身（clone） | 建 |
| `add <app> --rediscover` | 任意 | 重新配置 / 重新探测（要看下一步） | **建**（重探 + 建实例） |
| `add <app> --rediscover --profile-only` | 任意 | **重新探测（rediscover）** | **不建** |
| `add <app> --profile-only` | 无档案或失效 | 同「重新探测」 | 不建 |

**`--rediscover` 单独用 ≠ GUI 的「重新探测」**：前者会建实例，后者只落档案。二者只差 `--profile-only` 一个 flag，
必须在帮助文本里写明，否则用户以为"命令行重探一次"与界面同义，结果多出一个分身。

### 6.1 产品主流程（普通用户视角，控件级）

```
打开 appclone-gui（单窗口，AdwNavigationView 承载三屏；屏3 内部有四态（探测中 / 确认 / 创建中 / 失败））
  ① 列表页 ← AdwToolbarView{ AdwHeaderBar(标题位 = AdwViewSwitcher), AdwViewStack }
      **两个平级视图，各自滚动**：「分身」= 已开启的（管理既有），「所有应用」= 未开启的（挑选新增）。
      不把两组上下叠在同一页——一条滚动跨两个语义区，用户不知道自己在管谁。首屏落点：已有分身 → 「分身」，
      一个都没有 → 「所有应用」（点亮开关是唯一能做的事），只决定首屏一次；创建成功后切回「分身」。
      「所有应用」顶部：GtkSearchEntry「搜索应用」——397 个应用靠翻是翻不到的（§6.1.1）
      「分身」分组「已开启分身」：每个已开启应用一行 AdwSwitchRow，subtitle 显示「N 个分身」/「N 个分身 · M 个运行中」
                          （M 是数出来的，不写死 1——两个分身同时开着却说 1 个，用户以为另一个挂了）；
                          组底一行 AdwActionRow「添加应用分身」切到「所有应用」
      「所有应用」      ：未开启的一行一个 AdwSwitchRow；无搜索词时只渲染前 30 个，组尾一行
                          AdwActionRow「显示全部 N 个应用」（N 是实际数量，不是写死的 397），点了展开（仍非虚拟化，见 §6.1.1）
      **空态只取代「分身」视图的列表，不取代「所有应用」**：无实例时该视图换成 AdwStatusPage
                          （icon +「还没有分身」+ 一句"在「所有应用」里点亮开关" + suggested-action「选择应用」）；
                          「所有应用」与标题栏的视图切换器**必须照常可达**——两者都断了，首启用户就看不到
                          任何开关（产品首启死路，回归有专项断言）
      条件横幅（**同时最多一条**，致命优先；致命出现时降级那条不显示——bwrap 都没装，谈 fuse 降级没有意义）：
        · bwrap 缺失     → 「分身功能不可用：缺少 bubblewrap」，**无按钮**（致命，**整页只读**：开关、行点击、搜索全停；
                          任何操作最终都要 bwrap，允许进详情只会让用户在一屏点不动的界面里迷路。"知道了"也不能解除环境缺失）
        · fuse 缺失      → 「探测将在兼容模式下进行，结果可能不完整」+「了解」
                          （「了解」只收起这一条横幅，**不改变降级这个事实**：探测页里那条仍在，见 ③-a）
  → 点亮某个开关 = 唯一主入口。**分派依据是档案状态，不是"有没有实例"**，两个布尔量必须分开：
      `has_profile`（`profiles.d/<app>.toml` 存在）与 `creatable`（`ValidateCreatable` + `ValidateBindable`：
      `paths` 非空、`Exec` 在盘上、`extra_binds` 的源存在）。
      **`creatable` 不要求 `paths` 的宿主目录已经存在**：探测只把写入写进 overlay 的 upper（宿主上还没有），
      而它们由 `CreateInstance`/`Run` 的 `prepareBindTargets` 补建。把它算成"档案失效"会让用户卡在
      "重新配置 → 仍然失效"的循环里（这个坑真踩过）。真正"起不来"的判定留给 `run` 的前置检查——
      部分失效的档案必须走「重新配置」，不能"能用几条用几条"。
      只看 `has_profile` 会把"档案失效"当成"可以复用"，造出一个什么都不隔离、启动即失败的分身（§6.3 `profile_stale`）。
      **五个入口五个标题**，标题必须点名当前在做哪件事：
      · 从没配过（`!has_profile`）     → ③-a 探测中（必须跑一遍探测），标题「首次配置 · X」，确认按钮「创建分身」
      · 档案失效（`has_profile && !creatable`）→ ③-a 探测中（**要重探**），标题「重新配置 · X」，确认按钮「创建分身」——
        不能复用失效档案（造出启动即报错的分身），也不能只存档案（用户要的是能用的分身）
      · 配过但关掉了（`has_profile && creatable`，无实例）→ 直接 ③-b，标题「开启分身 · X」——复用档案、跳过探测，确认按钮「开启分身」
      · 详情页「＋新建分身」   → 直接 ③-b，标题「新建分身 · X」，确认按钮「创建分身」——
        动作与"开启"相同但要的是"再一个"，不能混称；若档案已失效则退回「重新配置」
      · 详情页「重新探测」     → ③-a 探测中（**要重跑**），标题「重新探测 · X」，确认按钮「保存档案」；
        只更新档案，**不建实例、不动既有分身数据**
      标题不能靠"有没有实例"猜：把"配过但关掉了"说成「首次配置」，用户会以为档案白做了，还白等一分钟探测
  ③ 探测页（自动 push，**四态**：探测中 / 确认 / 创建中 / 失败；**闸门失败也落 error 态，但必须带原因**）
     **进 probing 之前先跑四道闸门**（discover.md §4）：bwrap 不可用 / 缺 fuse（→降级横幅，**不阻断**）/
     目标应用还在运行 / 拿不到全局写锁。**任一硬闸门失败 → 直接进 error 态并带对应原因，开关回弹到关**，
     不启动探测会话。"应用还开着"是最高频的首启失败，绝不能让用户看到"没跟踪到任何写入"——
     那会把闸门失败误诊成"这个应用不写盘"，然后反复重试。
     **error 态的 `Reason` 至少四类**：`app_running` / `env_unavailable` / `no_writes` / `public_dir_leak`，
     每类一条独立文案（i18n 键分开）；**禁止所有失败共用一句"探测失败"**。
     ③-a 探测中 ← AdwToolbarView + AdwPreferencesPage
          顶部 AdwBanner（若已降级到 strace：**从探测中起就常驻，切到确认态也不消失**；
                         列表那条被「了解」收起后这里仍要在——push 页盖住了窗口顶部横幅，
                         而确认勾选恰恰是最需要知道"结果可能不完整"的时刻）
          居中 GtkSpinner + 「正在跟踪「微信」的写入…」
          实时行：已发现 N 个写入条目（流式追加，让人看见在动；**不是"命中次数"**，见 ③-b）
          提示语：「在应用里正常用一会儿——收发文件、改设置——然后关掉它」
          顶部 HeaderBar：「取消探测」（**必须有**，探测十秒到一分钟；确认态与失败态才叫「取消」）
     ③-b 探测确认 ← AdwPreferencesPage + 同一个 AdwBanner（降级时保持可见）
          分组「应用自身数据（建议隔离）」：可勾 AdwSwitchRow，subtitle = 路径 + **观测到的写入条目数**
                                          （**不是"命中次数"**：overlay 只知道"写过/删过"，拿不到次数；
                                           写次数就是承诺了 core 给不出的数据，实现时只能瞎编）
          分组「数据来源」            ：`AdwSwitchRow`「从现有应用数据克隆起步」，**默认关**，副标题
                                          「写时复制继承当前应用数据，不复制文件，主实例数据不会被改动；
                                          需要 fuse-overlayfs」。只在本入口真要建实例时出现
                                          （setup/open/clone/reconfig）；**rediscover 只更新档案、
                                          不建实例，必须隐藏**——否则开关看起来生效、实际什么都不做；
                                          **fuse-overlayfs 不可用时禁用**（run 期每个路径都会降级，
                                          拨了只会得到一个空实例）。与 CLI 的 `--fork` 写同一份
                                          `instance.toml` 字段，两端默认都不 fork
          分组「单例处理」            ：检测到锁/DBus/runtime 时出现，可勾
          分组「公共目录（强制共享）」：**不可勾的 AdwActionRow + .dim-label，只读展示**（一律显示，不是"有才显示"）
          分组「共享但可写（不隔离）」：`shared_writes` 的界面可见性。只读，**且必须写清代价**
                                          （"两个分身的最近文件会混在一起"、"输入法状态共享"）。
                                          代价不写出来，用户遇到就判定产品坏了——而这是有意为之的取舍
          顶部 HeaderBar：「取消」/「创建分身」（suggested-action，全不勾时禁用；
                                          open 入口为「开启分身」、reconfig 为「创建分身」、rediscover 为「保存档案」）
     ③-c 创建中 ← 同一个 HeaderBar：「正在创建…」（disabled）、「取消」也 disabled
          写档案 + 建实例目录 + 生成 .desktop 是几百毫秒的事务，**必须显式占住**：
          再点一次确认会建出两个实例（两次 `CreateInstance` 都通过校验），中途取消会留下
          "档案写了、实例没建成"的半成品。**独立态而非 confirm 里的一个 flag**；
          事务进行中 Esc 也不生效（关闭路径统一在 `CancelDialog` 里判 `state == creating` 后拒绝）
     ③-d 探测失败 ← AdwStatusPage：原因 + 「重试」（"没跟踪到任何写入"也走这一态，不生成空档案）。
          「重试」**恒可用**：它不能沿用上一态算出来的 disabled——失败态只有「重试」与「取消」两条出路，
          留一个点不动的按钮，用户只能关窗口。
          **唯一例外：档案拒绝加载**（`err.profile.version_ahead` / `err.profile.parse`）。重跑只会读到
          同一份档案，重新配置/重新探测若继续探测还会把它覆盖掉（§5.5），所以这一态不给「重试」：
          标题写明原因（如「档案由更新版本生成」），只留「取消」。复用档案（开启/新建分身）与
          重新配置/重新探测四个入口同一规则——「重试」按"有没有可重试的动作"显隐，不按状态名。
  → 确认后 goroutine 建实例 + 写档案 + 生成 .desktop，完成后 AdwToast「已创建分身」，
    然后 **replace 成详情页**（不是 pop：探测页是从列表 push 的，pop 只能回列表，
    而用户此刻该看到的是刚建出来的实例；replace 也避免返回栈里留一个已失效的探测页）
  ② 详情页 ← AdwPreferencesPage
      AdwPreferencesGroup「分身实例」：每行 AdwActionRow（名称 + 运行状态）+ 尾部动作：
      已停止为「启动」，运行中换成「停止」（二次确认，默认取消）；运行中「删除」禁用
      （tooltip 说明先停止，与 `rm` 的退出码 7 同源）、「重命名」禁用
      AdwPreferencesGroup「档案」：隔离路径数、探测方式与置信度、**共享但可写（`shared_writes`）**、
                                  单例处理、最近审计结论（§6.5）、实例根目录
      **置信度只说证据来源与覆盖范围，不许出现"结果完整 / 全部已捕获"**（见本节末"文案红线"）
      重命名用 AdwEntryRow；删除走 AdwAlertDialog（destructive，「移到回收站」，**默认响应是「取消」**）
      新增分身走「＋ 新建分身」行 → ③-b（沿用现有档案，跳过探测）
      重新探测走档案组「重新探测」按钮 → ③-a → ③-b（**只更新档案，不新建实例**）
  → 分身图标出现在 GNOME 概览（Name 带「（分身 <显示名>）」后缀），点开即用
  关闭开关（列表页）→ AdwAlertDialog 二次确认：「关闭「微信」的分身？N 个分身的数据将移入回收站」
      确认 → 全部实例 + 入口 gio trash；取消 → 开关**回弹到开**（不是留在一个假状态）
      **有实例正在运行时先拒绝**：「请先在应用里退出正在运行的分身」——与 `rm` 的退出码 7 同一判定，
      关闭开关不能比删单个实例更宽松（界面比 CLI 宽松 = 把契约撕开一个口子）
```

整个流程中用户**不接触**命令行、档案文件、strace 输出——复杂度全部由
discover 管线（[discover.md](discover.md)）与语义分类消化。

**七条不可省的 UI 约束**（每条都对应一个真实失败模式）：

1. **探测必须有四态且可取消**：`探测中 / 确认 / 创建中 / 失败`。探测要跑用户应用，十秒到一分钟都可能；
   模态对话框堵窗口会让用户以为卡死；"点完开关一片空白"会被当成坏了；确认到落地之间没有 `创建中`，
   连点两下就建出两个实例。
2. **降级必须显式告知，且要在两个地方说**：走 strace 兜底时用 `AdwBanner` 常驻说明，不许静默降级。
   列表页那条可以「了解」收掉（用户已经知道），但**探测页里必须还有一条**——窗口顶部那条在 push 页里
   被遮住，而确认勾选恰恰是最需要知道"结果可能不完整"的时刻。"收起横幅"不等于"降级消失"。
3. **两组"不隔离"的路径都必须出现在确认页**：`公共目录（强制共享）` 与 `共享但可写（不隔离）`。
   前者是"没有商量余地"，后者是"商量过了，代价是这样"。用户看得见哪些被排除、哪些被共享，
   才会相信工具没有乱来——这是第一原则在界面上的可见证据。
4. **关闭开关必须二次确认，且破坏性对话框的默认响应是「取消」**：关掉开关等于删除该应用的全部实例数据
   （进回收站）。一步误点的代价是"聊天记录没了"。把「移到回收站」设成 default response，
   等于键盘用户按回车就删——对话框存在的意义正是"不要一键删"。
5. **删除/关闭都要说清去哪**：对话框正文必须出现「回收站」而不是「删除」——用户要知道能找回。
6. **空态不能把入口藏掉**：`AdwStatusPage` 只取代**「分身」视图**的列表，「所有应用」与标题栏的
   视图切换器照常可达（空态里另有「选择应用」按钮）。首启用户若看不到任何开关，而引导语又把他指向
   一个到不了的地方，产品就死在第一次打开。拆成两个视图不改变这条不变式：首启仍有两条看得见的路。
7. **失败必须带原因**：`app_running` / `env_unavailable` / `no_writes` / `public_dir_leak` 四类各有独立文案与
   "下一步做什么"，**禁止所有失败共用一句"探测失败"**。尤其"应用还开着"是最高频的首启失败，
   若它显示成"没有跟踪到任何写入"，用户会把闸门失败误诊成"这个应用不写盘"，然后反复重试。

**文案红线（这几句话在实现里会变成事故，直接禁写）**：

| 禁写 | 改成 | 为什么 |
|---|---|---|
| 「命中 N 次」 | 「观测到 N 个写入条目」 | overlay-diff 只能回答"这个路径被写过/删过"，拿不到次数。写次数，实现期只能编 |
| 「结果完整」「全部写入已捕获」 | 「覆盖本次会话实际发生的写入（没走到的功能分支查不到）」 | 没走到的分支（换账号、点进某个设置页）根本不会出现在 upper 里。承诺完整 = 用户不再复核，漏隔的目录永久漏掉 |
| 「已隔离」（对 `shared_writes`） | 「共享，代价是…」 | 这类路径两实例共用一份，说成隔离就是事实错误 |
| 「探测失败」（单一文案） | 按 `Reason` 分行 | 见第 7 条 |

**一版就必须有勾选界面（屏3）**：ADR-006 原定"一版只做列表+开关，勾选放二版"已修订（见 [tech-stack.md](tech-stack.md) ADR-006）。理由是没有屏3 时，自动生成的档案直接生效——一旦误判就是把公共目录隔离掉，正好踩中项目第一原则。**宁可一版少一个功能，也不能让探测结果不经确认上线。**

#### 6.1.1 397 个应用怎么放（规模问题，不是审美问题）

实测 `/usr/share/applications` 有 **397 个 `.desktop`**（§6 来源表）。`AdwPreferencesPage` 的分组列表**不是虚拟化列表**
（`AdwPreferencesGroup` 内部是普通盒子，不是 `GtkListView`），一次性建 397 个 `AdwSwitchRow` 会明显拖慢首次显示。
三条对策，全在 `core` 与列表页，不进用户视野（决策见 [tech-stack.md](tech-stack.md) ADR-024）：

| 问题 | 对策 |
|---|---|
| 首次启动扫 397 个文件 | `core` 并发解析（`Exec`/`Icon`/`Name`/`NoDisplay`），结果写 `cache/apps.toml`，带每个源文件的 `mtime+size` 校验；只重解析变化的 |
| 渲染太多行 | 默认只渲染前 30 个（按"上次用过 > 已开启 > 字母序"排），组尾「显示全部 N 个应用」展开；**有搜索词时渲染全部匹配项**（上限 100，超出提示"再输入几个字"） |
| 找不到应用 | `GtkSearchEntry` 按显示名与 desktop id 双字段过滤，大小写不敏感；搜索结果**同时匹配英文名与本地化名**（`Name` 与 `Name[zh_CN]`） |

输入侧两条硬要求（不做就是输入框顿挫，用户以为程序卡了）：

- **防抖 120ms**：`GtkSearchEntry` 的 `search-changed` 本身已是防抖语义，但「按每次 `changed` 就重建列表」会把
  400 行 × 每个按键重建一遍；实现上仍要合并到一帧后统一重排（GUI 用 `glib.timeout_add` 120ms 单次定时器）。
- **命中封顶 100 并提示**：超过上限时组尾给一行「已显示前 100 个匹配（共 N 个），再输几个字缩小范围」，
  **不许静默截断**——截断而不说，用户会以为那个应用不存在。

**不做 `GtkListView` 虚拟化**：那要把三屏的 boxed-list 观感全部改成 list-view 样式（GNOME 设置页不用它），
为一个 400 行列表牺牲整个视觉一致性，代价与收益不对称。数量级到四位数再谈。

**搜索只作用于「所有应用」视图**：搜索框在那个视图里；「分身」视图不参与过滤，切回来时列表完整
（已开启的应用仍能在那里找到并进详情）。搜索不会把任何分组藏起来——它只改 `all` 视图的行集合。

探测的完整方案谱系（overlay-diff 主探测 + 静态预填 + 语义分类三层管线）见 [discover.md](discover.md)。

### 6.2 单例/互斥问题（双开的真正难点）

应用"双开"失败通常不是目录问题，而是单例检测。**三种机制必须分开处理，混用会直接导致应用起不来**：

1. **普通文件锁**（`flock`/`O_CREAT` 固定路径）→ 写入 `lock_files`。
   原理：mount 一个 inode 不同的私有空文件盖在上面，`flock` 自然不再互斥。**这是唯一能用"bind 空文件"解决的形态。**
2. **DBus well-known name**：应用启动时在 session bus 上抢名字，抢不到就把参数
   转发给已有实例后退出 → `isolate_dbus = true`（起私有总线，daemon 生命周期见 §6.6）。
   副作用：托盘、通知等会话集成在分身内失效，GUI 需提示这一取舍。
3. **unix socket 型单例**（`$XDG_RUNTIME_DIR/*.sock`）：Electron 系常见 → `isolate_runtime = true`
   （目录生命周期见 §6.6）。
   **这一条的成败全在"共享进来的是哪几个 socket"，必须有明确清单**（原写法"wayland/pulse/bus 逐个 bind"漏一样就残一样）：

   | 类别 | 路径（`$XDG_RUNTIME_DIR` 下） | 漏了会怎样 |
   |---|---|---|
   | Wayland 显示 | `wayland-*`（值取 `$WAYLAND_DISPLAY`，缺省 `wayland-0`；用通配匹配 `wayland-<n>`） | 没有窗口 |
   | PulseAudio / PipeWire | `pulse/native`、`pipewire-0` | **没有声音**（`pipewire-0` 最容易漏） |
   | 会话总线 | `bus`（`isolate_dbus = false` 时） | 托盘、通知、输入法全失效 |
   | dconf | `dconf/user` | 设置改了不持久 |
   | 无障碍 | `at-spi/bus*`（**实际文件名是 `at-spi/bus`，不一定是 `bus_0`**——按通配匹配） | 读屏/辅助功能失效 |
   | X11（X11 会话才有） | `X11-unix/` | X11 会话下没有窗口 |

   规则：**只读 bind（`--ro-bind-try`）**，逐个按存在性跳过（`-try`），并**只 bind socket/目录本身**，
   不 bind 整个 `$XDG_RUNTIME_DIR`（那会把宿主单例 socket 一并带进来，等于没隔离）。
   实现上由 `core.RuntimeSockets()` 产出这个清单（探测存在性在调用方），`BuildBwrapArgs` 只负责排序拼装（§3.1 ⑨）。
   **禁止把 socket 路径塞进 `lock_files`**：普通文件 bind 到 socket 路径后，应用 `connect()` 会 `ENOTSOCK`，表现是"分身启动即崩"，不是"绕过单例"。
   若应用写死了 socket 绝对路径且不读 `XDG_RUNTIME_DIR`，则无法分身 → 标 `unsupported` 并写明原因。

### 6.3 失败语义（每一条都要有明确结果，不许静默）

退出码即"哪一类失败"，脚本与 GUI 都靠它分支，**不要按提示文案判断**：

| 码 | 类别 |
|---|---|
| 0 | 成功（含已告知的降级；含 `verify` 的 `verified` 与 `unverified`——后者是"不知道"，不是失败） |
| 2 | 输入/档案不合法（找不到应用、`Exec` 解析失败、档案版本超前、`paths` 含公共目录、**`paths` 里的源已不存在 = `profile_stale`**） |
| 3 | 环境不可用（bwrap 缺失 / userns 被禁） |
| 4 | 探测无结论（样本不足 / 零写入 / 公共目录摘出失效） |
| 5 | 冲突（实例已存在 / 拒绝删除） |
| 6 | 并发（拿不到全局写锁 / 目标应用正在运行） |
| 7 | 状态不允许（要删的实例正在运行） |
| 8 | 隔离校验发现泄漏（`verify` = `leak-detected`） |
| 1 | 内部错误 / 用法错误（panic 兜底、未归类的 bug）——**留给 appclone 自己，不要复用** |

**`run` 的退出码必须与应用退出码分层**（原表只有 appclone 自己的码，而应用完全可能返回 2~8，
脚本会把应用的"2"读成"输入不合法"、把"8"读成"隔离泄漏"，契约被 `run` 一个命令撕开）：

| 情形 | `run` 的退出码 |
|---|---|
| 正常启动、应用正常退出（0） | 0 |
| 正常启动、应用非零退出 | **1**（不猜应用码的含义） |
| 需要原样拿到应用码（脚本场景） | 加 `--propagate-exit`，此时原样返回应用的退出码 |
| 被信号杀死（应用或 `run` 自身） | `128 + signal`（如 SIGTERM → 143） |
| appclone 自身失败（环境/档案/锁/运行态） | 3 / 2 / 6 / 7（按上表），**永远不与应用码混用** |

`--json` 输出里应用码与信号单独成字段（`app_exit_code` / `signal`），调用方不必自己减 128。

| 情形 | 行为 | 退出码 |
|---|---|---|
| 应用不在三个来源目录 / 无 `Exec=` | 报"找不到应用/无启动命令"，不建目录 | 2 |
| `Exec=` 解析出相对路径或含未剥离字段码 | 报解析失败并打印原始 `Exec=` 行 | 2 |
| 档案 `version` 大于当前 | 报"由更新版本生成"，**不猜字段** | 2 |
| 档案 `paths` 含公共 XDG 目录 | 拒绝加载该档案并指出具体路径（不是忽略这一条） | 2 |
| bwrap 不存在或 user namespace 被禁 | 报环境不可用 + 给出 `sysctl` 检查命令，**不尝试 fallback 到 root** | 3 |
| 目标应用已有实例在运行（探测前闸门） | 提示"请先完全退出「X」"，**不启动探测**（继续只会得到零写入和一条假结论） | 6 |
| 拿不到 `AC_BASE/.lock`（等 5 秒超时） | 报"另一个 appclone 正在操作，请稍后重试" | 6 |
| 探测中途用户退出应用（会话过短） | 报"探测样本不足"，**不生成档案**、不留半成品实例；探测临时区（`probe/`）按 §4 约定清空 | 4 |
| 探测结果为空（本次零写入） | 报"未观测到写入"，建议重跑，不写空档案 | 4 |
| 探测结束发现 `probe/upper` 里有公共目录路径 | 报"探测未正确共享公共目录，结果已作废"，**丢弃全部候选**（§4 清理约定仍执行） | 4 |
| 实例同名已存在 | 列出已有 id 并报错，不改动已有实例 | 5 |
| `rm` 时目标不是 `gio trash` 能处理的路径 | 拒绝并报错，**绝不 `rm -rf`** | 5 |
| 探测时目标应用还有进程在跑 | 提示「请先把「X」完全退出」，**不给"仍然继续"** | 6 |
| 探测会话没能跑起来（userns 被禁 / Exec 不存在 / bwrap 启动失败） | 报具体原因，**不产出档案**；与"应用没写盘"区分 | 3 |
| 探测命中公共目录污染（摘出失效） | 结果作废、`quarantine-*` 保留现场、打印恢复路径 | 4 |
| 探测超时或零写入 | **不生成空档案**，说明下一步（把应用真正用一遍再试） | 4 |
| `rm` 一个正在运行的实例 | 拒绝并提示"请先在应用里退出它"，**不替用户杀进程** | 7 |
| `isolate_dbus` 但没有 `dbus-daemon` | 降级为共享总线 + 明确告知"可能无法双开" | 0（降级成功） |
| 探测/运行中 `fuse-overlayfs` 不可用 | 明确"已降级到 strace"，并把这条写进档案的 `probe_method` 字段 | 0（降级成功） |
| `doctor --verify` 结论 `verified` | 输出"未发现越界写入"+ 摘要（时间、覆盖范围） | 0 |
| `doctor --verify` 结论 `leak-detected` | 列出越界路径清单 + 建议重探测 | 8 |
| `doctor --verify` 没有审计证据 | 输出 `unverified` + 一句"未开启审计，无法判定"，**不输出通过** | 0 |
| `doctor --verify` 时实例正在运行 | 拒绝读半截证据，报"请先退出该分身" | 7 |
| 档案 `paths` 为空（只勾了缓存/单例） | 报"没有可隔离的应用数据"，**不创建档案、不建实例** | 2 |
| `add <app>` 但应用 key 非法（含 `/`、`..`、非 ASCII 等） | 拒绝并说明合法字符集，不建任何目录 | 2 |
| `add ` 或 `run` 时 `exec` 不存在（应用升级/卸载后路径变了） | 报"启动命令不存在，可能已升级，请重新探测" | 2 |
| 档案 `paths` 里的源**已不存在**（应用升级换了数据目录 = `profile_stale`） | **`run` 直接拒绝**（bwrap 的 `--bind` 源不存在会整条命令失败，报错发生在容器里、用户看不懂）；GUI 把该应用标成「档案已失效」并引导「重新配置」 | 2 |
| `run` 但实例不存在 | 列出该应用已有实例，报"没有这个分身" | 5 |
| 同一实例第二次 `run` | 报"该分身已在运行"（不阻塞、不转发） | 7 |
| `rm` / 关闭开关时 `gio` 不可用 | 报环境不可用并提示安装 `glib2` 提供的 `gio`，**绝不回退到 `rm`** | 3 |
| 探测/审计写层被判定"与 lower 嵌套"（§4.4 断言失败） | 报环境/配置错误，**不挂载、不删任何东西** | 3 |
| 公共目录摘出反向断言命中（探测期） | 报"探测未正确共享公共目录，结果已作废"，**保留 upper 现场供找回**，不删 `probe/upper` | 4 |

清理约定：失败时只删**本次新建**的空目录，绝不动既有实例与档案。
**唯一的例外是"可能含用户文件"的情况**：探测期反向断言命中、审计期发现越界，都说明 upper 里可能有用户文件——
此时**一律不删 upper**，改名到 `quarantine-<时间戳>/` 并把恢复路径打进错误信息（探测区在 `/var/tmp`，
审计证据区在实例目录，见 §4.4）。"临时区必须清空"这条规则到此为止，**没有任何理由让它压过"不删用户文件"**。

### 6.4 环境变量（测试与多环境用，产品路径不需要）

| 变量 | 作用 | 缺省 |
|---|---|---|
| `AC_BASE` | 覆盖运行时根（`~/.local/share/appclone`） | XDG data dir + `appclone` |
| `AC_HOME` | 覆盖探测/运行时视为的 `$HOME` | 真实 `$HOME` |

两者主要用于隔离冒烟（假 HOME），**GUI 不暴露、不读取用户手填值**。

**路径解析必须只有一份实现**（`core.PathResolver`，CLI/GUI/探测/审计共用）：输入 `AC_HOME`（可选）、
`XDG_*`、uid；输出绝对路径。规则：

- `~` 与 `$HOME` **一律按有效 HOME 展开**：设了 `AC_HOME` 就是 `AC_HOME`，否则是真实 `$HOME`；
- `$XDG_CONFIG_HOME` 等变量按目标环境解析，变量为空时用 XDG 规范默认值（不是硬编码 `~/.config` 字符串拼接）；
- 展开后 `Clean`，再 `EvalSymlinks` 成真实路径（软链是常态：用户可能把 `~/.config` 链到别处；
  链到 `$HOME` 之外时，探测的 overlay 看不到 → 必须报"软链逃逸"并标 `unsupported`，不许静默隔离失效）；
- 相对路径、`..`、空串一律拒绝（退出 2）；
- `paths` 落盘时优先存 `~/...`（可移植），软链或 XDG 变量指向别处时存绝对路径——
  **存哪种由"能否用有效 HOME 无损还原"决定**，不是随手 `fmt.Sprint`。

`AC_HOME` 一旦与真实 `$HOME` 不同，`BuildBwrapArgs` **必须同时产出 `--setenv HOME <AC_HOME>`**
（§3.1 的 `--setenv HOME` 那条）。只把 bind 目标换成 `AC_HOME` 而环境变量不动，应用仍按真实 `$HOME` 找路径，
冒烟测试会"看起来隔离成功"（实例目录里确实有文件），实际跑的是未隔离的宿主数据——
这是最危险的一类假通过：**测试写对了，被测对象没变**。`doctor` 启动时若发现 `AC_HOME != $HOME`
且 `--setenv HOME` 缺失，直接报配置错误。

**探测期也走同一条规则**：overlay 的 lower 与 `--bind merged <目标>` 的目标都是**有效 HOME**，
`--setenv HOME` 同样必须产出。原 discover 参考序列里写死 `$HOME`，在假 HOME 冒烟下会把真实主目录当 lower——
测试看着通过、实际探测的是用户真实家目录（§7 的 F 项就是这么被写成假通过的）。

### 6.5 运行期审计与 `doctor --verify` 的可行口径

**先说清能力边界**：没有审计层时，"应用有没有写到实例目录之外"**无法归因**。
免 root 条件下能用的手段（fanotify 需 `CAP_SYS_ADMIN`、eBPF 普遍被 `unprivileged_bpf_disabled` 关掉、
inotify 无 PID）都不成立——这与 [discover.md](discover.md) §2 的谱系结论一致。
所以 `doctor --verify` 不做"假装能看见"的检查，而是**复用探测期的 overlay 机制**：

```
运行期审计层（--audit 或档案 audit=true 时启用）：
  lowerdir = 有效 HOME（ro）
  upperdir = /var/tmp/appclone/audit.<uid>/<app>.<id>/upper    ← 必须与 lower 物理分离（§4.4）
  workdir  = /var/tmp/appclone/audit.<uid>/<app>.<id>/work
  merged   → bwrap --bind 到 有效 HOME
  然后按顺序再 bind（顺序即语义，与 §3.1 完全一致）：
    ① 公共目录摘出清单 → 真实目录 rw（**与探测期同一份清单、同一份实现**：清单来源见
       [discover.md](discover.md) §3.2.1，界面上同一份展示在 §6.1 ③-b 的「公共目录」组）
    ② AC_BASE / shared_writes → 真实路径（同探测期，缺了会把工具自己的写入算成泄漏）
    ③ 实例私有目录     → 实例 root 下（数据落持久层，**必须排在 ①② 之后**：
       排前面会被公共目录 bind 盖掉，应用数据反而落进 upper；`verify` 把"本该被 bind 走的路径
       出现在 upper 里"一律判成 bind 失效（见下方优先级段），所以这个错会被直接指出来）
  `audit/` 目录本身（实例内）只放 run.toml / summary.toml / quarantine-*/ 这些轻量证据元数据
```

**① 不是可选项，是本节的准入条件**：审计层把整个 `$HOME` 罩住，若不把公共目录、`AC_BASE`、`shared_writes`
bind 回真实目录，审计运行期间用户往 `~/Downloads` 存的文件会落进写层 `upper`——而这段逻辑一旦出错（或用户取消、
或进程被杀），删 upper 就是删用户刚存的文件。这与 discover.md §3.2.1 定为"第一红线"的是同一事故，
所以**摘出清单必须由 `core` 单一实现、探测与审计共用**，不允许各写一份（ADR-018 ①）。

**审计层必须复用探测期那条反向断言，而且后果更重**：运行结束、删除任何东西之前，
检查写层 `upper` 里是否出现公共目录 / `AC_BASE` / `shared_writes` 的路径。命中即说明摘出失效——
此时**一律不得删除写层 `upper`**，保留现场并标记本次审计作废（退出码 4），
提示用户"审计期间有文件可能写进了隔离层，尚未删除；请检查 ~/Downloads 等目录，缺失的文件可从
工作区 upper 找回（verify 会把它搬进 `audit/quarantine-*` 并给出路径）"。探测期作废只是白跑一趟，审计期作废**可能是用户文件已经落进 upper**，
所以"先删再查"在这里不是顺序问题，是数据丢失问题。

**留存策略（不能"运行结束即删"，否则 verify 永远读不到证据）**：

| 时机 | 动作 |
|---|---|
| `run --audit` 开始前 | 上一轮 upper 还有内容 → **先搬到** `audit/quarantine-<唯一名>/`（保留文件、不阻塞新审计），再清临时目录。同时用一条 `finished_at` 为空的**进行中凭证**顶掉上一轮 `run.toml`（不是简单删除）：新审计若在写层建立前就失败，verify 见到的是 `audit_incomplete`，不会把旧 `summary.toml` 重放成"本次通过"。旧实现"直接拒绝"会让取回文件后的用户永远无法再审计，唯一出路是手工删文件——复杂度泄漏给用户（ADR-013 口径） |
| 运行结束 | **保留**写层 `upper`（工作区 `/var/tmp/.../upper`），并把 `audit/run.toml` 补成完整凭证（`finished_at` 非空 + 退出码 + 本次**实际** bind 回真实的 `public_binds` / `shared_binds` / `paths` / `base`）——`finished_at` 非空才是"这次审计正常跑完"的凭证，也是 verify 判摘出的唯一依据 |
| `doctor --verify` | 先 `LOCK_NB` 拿 `run.lock`（拿不到报"实例在运行"，退出 7）；读 upper + `run.toml` 对账，写 `audit/summary.toml`，**只有结论为 `verified` 时才删 upper 与 run.toml** |
| 结论是 `leak-detected` | **不删 upper**：越界文件就在里面，删掉等于销毁用户数据（应用可能把用户文件写到了 `paths` 之外）。改为搬进 `quarantine-<时间戳>/` 保留，`summary.toml` 记 `evidence_retained = true`，并打印恢复路径 |
| 用户再次 `run --audit` | 回到第一行（`quarantine-*` 不自动清，只由用户手动处理） |

所以 `audit/` 里长期只有 `summary.toml`（几 KB）+ 每轮作废时留下的 `quarantine-*`，不是"无主增长"的临时区——
`quarantine-*` 里装着**可能属于用户的文件**，所以它**永不自动删**，只由用户手动处理（§7 的安全要求），
生命周期由 verify 管理。overlayfs 需要的 `work/`（workdir）与 `merged/`（挂载点）是**真正的临时区**：
与 upper 同在 `/var/tmp` 的工作区，run 结束即删，不进 verify 的读取路径。

这样运行期的每一次实例外写入都物理落在写层 `upper` 里，与 `paths`/`shared_writes` 对账即得结论：

**对账算法必须写死**（原写法只有一句"路径是否都在声明范围内"，会让实现各写一套）：

- 单位是**叶子条目**：upper 里的每个非目录条目、以及 whiteout（删除动作），各自取相对 `$HOME` 的路径；
  **纯父目录不单独判越界**——`~/.config` 出现在 upper 只是因为它下面有 `~/.config/App/…` 的写入，
  直接判它越界会把一切正常应用报成泄漏；
- 路径先 `EvalSymlinks + Clean` 再比较；`paths`/`shared_writes` 的**目录按前缀匹配**、**文件按精确匹配**；
- `ignored`（档案字段，默认 `~/.cache`/`~/.thumbnails`/`Trash`/`~/.local/state`）命中即跳过，
  但**必须计入 summary 的"已忽略类别"**，不许悄悄忽略；
- 命中 `shared_writes` 的写入算验证通过（它们是"预期共享"）；命中 `unsupported` 的**不参与判定**
  （那类东西本来就不在文件路径上，用路径判定没有意义）。声明过、但审计开始时不存在因此没被
  `--bind-try` 绑上的 `shared_writes` 同样算通过：应用在审计期间把它建出来不是越界。

**覆盖范围必须写在结论里**：审计只覆盖有效 `HOME` 之下。`/tmp`、`/var`、`/opt`、`extra_binds`
都不在证据里——所以 summary 与 GUI 都要标明"覆盖 = `$HOME`"，**不许把"没看到越界"说成"全局无泄漏"**。

| 审计层 | 对账结果 | 输出 |
|---|---|---|
| 有 `upper` + `run.toml`（`finished_at` 非空 = 正常跑完），写入全部落在 `ignored`（噪声）∪ `unsupported`（不在文件路径上）内 | 对账通过 | `verified` |
| 有 `upper` + 已完成的 `run.toml`，出现范围之外的目录 | 越界 | `leak-detected` + 路径清单 + 建议重探测 |
| 有 `upper` 但**没有** `run.toml`，或 `run.toml` 的 `finished_at` 为空（上次 run 崩了或被 kill） | 审计没跑完，证据不完整 | `unverified`（"上次审计未正常结束"），**不删 upper** |
| 只有 `summary.toml`（upper 已被消费），且**没有**更新的未完成审计尝试 | **重放**已存结论，不重新对账 | 按摘要：verified 0 / leak 8 |
| 有"进行中"的 `run.toml`（`finished_at` 为空）但**没有** upper：新审计在写层建立前就失败/被杀 | 本轮审计根本没跑起来，旧摘要不适用 | `unverified`（`audit_incomplete`），**不重放旧 `summary.toml`** |
| `upper` 为空且 `run.toml` 完成 | 审计跑了但应用没写任何东西 | `unverified`（"没有观察到写入，无法判断是否隔离有效"）——**空集不算通过** |
| 三者都不存在 | 从没开过审计 | `unverified`（"未开启审计，无法判定"） |

**优先级：摘出失效压过对账（实现口径，2026-11-07 写死）**。上表第三节"反向断言"与本表有交叉：
`shared_writes` / `AC_BASE` / 公共目录本该被 bind 回真实位置，它们出现在写层 `upper` 里就说明摘出没生效。
这种情况一律判 `unverified` + `reason=extract_failed`（**退出 4**、`retained=true`），**不是** `leak-detected`：
两者**不能**互换地读：`leak-detected` 的下一步是"重新探测"，`extract_failed` 的下一步是
"先去 `audit/quarantine-*` 把可能缺失的用户文件取回来，再谈隔离"。`extract_failed` 时**不再单独列越界清单**——
摘出已经失效，任何"哪条是越界"的归因都不可信；代价是这次审计里真实的越界路径也会被这条结论吞掉，
所以它的输出必须同时提示"本次审计作废、请重跑"，而不是只报一个原因代号。

**"本该被 bind 走"的四个来源是一组**：公共目录、`AC_BASE`、`shared_writes`、**`paths`**。
它们出现在 upper 里都只有一个解释——那条 bind 没生效。`paths` 尤其如此：应用数据本该落在实例
root 下，落进 upper 就说明它被别的 bind 盖掉了（例如公共目录 bind 排在实例 bind 之后），
把这情形算"通过"等于把 bind 失败静默掉。**通过档只有两项**：`ignored`（噪声类别，本来就该进 upper）
与 `unsupported`（不在文件路径上，用路径判定没有意义）。

判据是"出现的路径是否都在声明范围内"，**不是"upper 是否为空"**：overlayfs 对 `O_RDWR` 打开、
元数据变更（chmod/chown/xattr）都会触发 copy-up，只读浏览也可能留下 upper 条目。
拿"空"当通过条件会把正常行为误报成泄漏；`noatime` 只能挡掉 atime 这一类，挡不掉其余。
但反过来说，**空集也不能算通过**——那说明应用这次根本没写盘，审计没覆盖到任何东西，
"没观察到"与"观察到没有越界"是两件事，只能给 `unverified`。
`verified` 的准确含义因此是"这次审计覆盖到了写入，且这些写入都在声明范围内"。

代价与取舍：审计层把整个 `$HOME` 过一遍 overlay，首次打开文件有 copy-up 开销，
所以**默认关闭**，只在这两种场景开：① 用户报"分身的数据跑到主空间了"；② 档案 `audit = true`（应用改路径频繁）。
GUI 不提供开关（避免把复杂度泄漏给用户），只在详情页展示最近一次审计结论与时间。

**`--verify` 的调用语义**：它读**上一次**运行留下的审计证据（写层 `upper` 或已归档的 `summary.toml`），
自身不启动应用；先拿 `run.lock`（拿不到 = 实例在跑，退出 7），对账完成后写 `summary.toml`；
**只有 `verified` 才删写层 `upper`**（见上方留存策略）。**幂等**：重复调用同一个未变的证据池返回同一结论；
已归档的 `summary.toml` 走"重放"，不再重新对账，也不会改变已保留的 `quarantine-*`。
要现跑现验就 `appclone run <app> <id> --audit` 一次再 `--verify`；两步分开是有意的——
把"跑应用"和"下结论"分开，避免 verify 变成一个会启动 GUI 应用的隐蔽命令。

**实现现状（2026-11-07）**：判定逻辑已完整落地，缺的只是"证据生产者"。`core/verify.go` 里
`Env.Verify` 覆盖上表全部六种情形（含 upper 有而 `run.toml` 缺 → `audit_incomplete`、
空 upper → `no_writes`、只剩 `summary.toml` → 重放、摘要损坏 → `audit_unreadable` + 保留），
`Env.Judge` 是纯函数（不读盘、不删任何东西），`core/verify_test.go` 逐条断言。
`audit/summary.toml` 的形状 = `conclusion` / `coverage` / `violations` / `ignored` / `evidence_retained` /
`generated_at` / `reason`；**`conclusion` 只接受三个枚举值**（`verified` / `leak-detected` / `unverified`），
其它值按"证据不可读"处理——手写 `conclusion = "OK"` 会让退出码是 0（通过）而 CLI 打印 unverified，
同一份证据两种说法。`reason` 同理（未知值降级成 `audit_unreadable`），否则 CLI 会说错"哪种不知道"。
`evidence_retained = false` **照实读 false**：那意味着越界文件可能已经从 `audit/` 里被删除，
CLI 必须提示"可能取不回"，而不是反过来断言"证据已保留"——把用户的明确记录改成相反结论，
是比缺失更坏的信息。
**verify 现在按结论处置证据**（`core/verify.go` 的 `finalize`，2026-11-07）：
`verified` → 写 `summary.toml` 并删掉 `upper` 与 `run.toml`（证据已消费）；
`leak-detected` → `upper` 改名 `audit/quarantine-<时间>/`（**不删**：越界文件就在里面），
摘要记 `evidence_retained = true`，输出里给出这个路径；
`extract_failed` → 与 `leak-detected` 一样把 upper **搬到** `audit/quarantine-<时间>/`（摘出失效时
upper 里可能就有用户文件，原地留着会让下一轮审计开始前的清理碰它们），摘要记
`evidence_retained = true` 并输出该路径；其余 `unverified` 不写摘要、不动现场。
**处置顺序是先搬/删、再写摘要**：反过来的话，摘要一旦写成功而处置失败，下一次 verify
会按"证据已消费"重放一个错误结论，现场再也找不回。
**写入器已落地**（2026-11-07）：`run --audit` 在 ④ 与 ⑤ 之间插入审计层（overlay 罩住 HOME →
公共目录/AC_BASE 绑回真实 → 实例私有目录），结束后**保留**写层并把 `audit/run.toml` 补成完整凭证；
写层路径是确定性的（`/var/tmp/appclone/audit.<uid>/<app>.<id>/upper`），verify 才能自己找到证据。
`run.toml` 从审计**开始**就存在（`finished_at` 为空 = 进行中），**完成与否只看 `finished_at`**：
这样"新一轮审计在写层建立前就失败"也会留下 `audit_incomplete` 的痕迹，不会退化成重放旧摘要。
`run.toml` 同时记**本次实际生效**的 `public_binds` / `shared_binds` / `paths` / `base` 与 `binds_recorded = true`：
verify 按这份现场清单判摘出，而不是按档案里"写了什么"猜——没配置或当时不存在的公共目录根本没被 bind，
写到它们不该算 bind 失效；审计之后用户重新探测改了档案，也仍按审计当时的 `paths` 归因。
没有 `binds_recorded` 的老凭证按档案回退推断（方向不能错：extract_failed 与 leak-detected 的下一步相反），
`run.toml` 写坏则降级为 `audit_incomplete`（保留现场），不报环境错误。
**残留清扫按实例判断**：写层目录名是 `<app>.<id>`，清扫前用 `run.lock` 的 `LOCK_NB` 探活，
并跳过已写完 `run.toml`（等 verify）的实例；只有无人认领的残留才搬进 `/var/tmp` quarantine。
读不出 upper（子树被 chmod 000 / IO 错误）同样**搬走**而不是删：看不见内容恰恰说明里面可能有用户文件。
两个实例同时审计时，后启动的那个不能卸掉前一个的挂载。
`audit_incomplete` 且 upper 已不在时，若 `audit/` 下已有 `quarantine-*`，结论必须带出**最新一份的真实路径**
（只说"证据已保留"而用户找不到目录，等于没告诉；upper 还在工作区时不得指向旧 quarantine，会把用户引到无关证据上）；
摘要写失败时错误信息同样必须带该路径。
没有审计的实例仍然是 `unverified` + `reason=audit_not_enabled`（退出 0，**不是通过**）。
`ignored` 为空时补 `DefaultIgnored()`：不给默认噪声白名单，任何真实应用都会被判泄漏
（正常启动就写 `~/.cache`），结论会变成噪声而不是信号。

**只补"缺字段"，不覆盖显式空数组**（`ignored = []` 是用户关掉噪声白名单的选择）；
`ignored`/`shared_writes` 里的条目要过校验：`~`、`/` 这类等于"全部放行"的值一律报 2
（`err.profile.blanket_path`），否则 `doctor --verify` 会对任何越界写入都说通过——
这是最危险的一类假通过。

**两处已知取舍（写下来免得当成 bug 反复讨论）**：
① `~/.local/state` 同时出现在 `DefaultIgnored` 与"可勾选的 XDG 根"里：它默认被当作噪声忽略，
用户主动勾选后它会进 `paths`；隔离生效时它的写入落在实例 root 下、**不会**出现在 upper 里，
所以"默认忽略"与"勾选后隔离"并不矛盾：前者是把它当噪声，后者是让它真正被隔离。
② `verify` 的 `run.lock` 守卫只在锁文件**已存在**时才 `LOCK_NB`：`verify` 声明为只读，不带
`O_CREATE`。理论上存在"锁文件尚未创建、run 恰好此刻启动"的窗口；`run` 自己会先建锁再干活，
这个窗口只有在该实例从来没被 run 过时才会出现，而那正是"没有 upper 可读"的情形。

### 6.6 私有 runtime 与私有 DBus 的生命周期

`isolate_runtime` / `isolate_dbus` 不是"加两个 bind 就完事"，它们各自带一个有生命周期的进程或目录
（决策见 [tech-stack.md](tech-stack.md) ADR-026）：

| 对象 | 谁创建 | 生命周期 | 结束时的清理 |
|---|---|---|---|
| `instances/<app>/<id>/runtime/` | `run` 启动时 `MkdirAll(0700)` | 随实例常驻（下次运行复用） | **保留**；里面只有 socket 与临时文件，下次启动前清掉上次残留的 `*`（不含目录） |
| 私有 `dbus-daemon` | `run` 用 `dbus-daemon --session --nofork --address=unix:path=<inst>/dbus/bus --print-address` 起子进程 | 与 bwrap 同生共死：bwrap 退出（或进程组被 kill）后 `run` 回收它 | 杀掉 daemon，删除 `dbus/bus` socket 文件 |
| wayland / pulse / session bus socket（**宿主**的） | 宿主会话 | 只读 bind 进私有 runtime | 不碰，只读挂载 |

三条实现约束：

1. **顺序**：先起 dbus-daemon（要它的 socket 存在才能 bind），再起 bwrap；bwrap 失败时立刻回收 daemon，
   否则留下一个没有客户端的 daemon 挂在用户会话里；
2. **`--nofork` 必须带**：fork 模式下 `--print-address` 的父进程会先退出，拿不到地址；
3. **地址不写死**：`DBUS_SESSION_BUS_ADDRESS` 用 `--print-address` 的输出（`unix:path=...`），
   不要自己拼 `unix:path=` 再假设格式——地址格式是 dbus 的实现细节。

失败语义：`isolate_dbus = true` 但系统没有 `dbus-daemon` 时**降级为不隔离并明确告知**
（"这台机器没有 dbus-daemon，分身将与主实例共用会话总线，可能无法双开"），
不要静默按共享跑——用户会以为是应用不支持分身。

## 7. 验证清单

**每条都要有正向 + 反向两个断言**，只验"该出现的出现了"不算通过——最常见的失败是"该出现的出现了，但不该动的也被动了"。

```bash
# 前置：全程用假 HOME，不碰真实主目录。
# **HOME 必须一起改**：只设 AC_HOME 的话，overlay 的 lower 仍是真实 $HOME，
# 下面 F 项会把用例文件写进假 Downloads、断言却盯着假目录，而实际探测的是你的真实家目录（假通过 + 潜在破坏）。
T=$(mktemp -d); REALHOME="$HOME"
export HOME="$T/home" AC_HOME="$T/home" AC_BASE="$T/home/.local/share/appclone"
export XDG_DATA_HOME="$T/xdg" XDG_CONFIG_HOME="$T/home/.config" XDG_CACHE_HOME="$T/home/.cache" \
       XDG_STATE_HOME="$T/home/.local/state" XDG_RUNTIME_DIR="$T/run"
mkdir -p "$HOME" "$XDG_RUNTIME_DIR"; chmod 700 "$XDG_RUNTIME_DIR"
mkdir -p "$HOME/.config/TargetApp" && echo old > "$HOME/.config/TargetApp/state"
test "$HOME" != "$REALHOME" || { echo "拒绝在真实 HOME 上跑验证"; exit 1; }   # 硬闸门

# A. 隔离生效（正）：分身写入落在实例目录
appclone run <app> <id>            # 应用内改一条设置后退出
find "$AC_BASE/instances/<app>/<id>/root" -mmin -5        # 期望：有文件

# A'. 隔离生效（反）：宿主对应目录一个字节都没动
find "$AC_HOME/.config/TargetApp" -mmin -5                # 期望：**无输出**
stat -c '%y' "$AC_HOME/.config/TargetApp/state"           # 期望：仍是创建时间

# B. 共享生效（正）：分身保存的文件出现在公共目录
ls -lt "$AC_HOME/Downloads" | head                        # 期望：新文件在列
# B'. 共享生效（反）：公共目录**没有**被 bind 到实例目录
findmnt -R "$AC_BASE/instances/<app>/<id>/root" | grep -c Downloads   # 期望：0

# C. 双开成立（正）
pgrep -af '<app>' | wc -l                                 # 期望：>=2
# C'. 双开成立（反）：两个进程的 mount namespace 不同
readlink /proc/$(pgrep -f '<app>' | head -1)/ns/mnt
readlink /proc/$(pgrep -f '<app>' | tail -1)/ns/mnt       # 期望：两个值不同

# D. 命名空间内确认替换（正 + 反）
appclone run <app> <id> sh -c 'findmnt -no FSTYPE,TARGET | grep TargetApp'
# 期望：bind 类型、目标为原路径（FSTYPE=bind 或 none），不是 overlay/ext4

# E. 参数契约（纯函数，不跑应用）
go test ./core -run TestBuildBwrapArgs -v   # 覆盖顺序、公共目录拒绝、特殊字符、setenv 配套

# F. 探测不碰用户文件（正 + 反）——探测期第一红线
echo keep > "$AC_HOME/Downloads/probe-marker"
appclone add <app>; echo "exit=$?"          # 探测会话里再往 Downloads 存一个文件
cat "$AC_HOME/Downloads/probe-marker"       # 期望：仍是 keep（没被 upper 吞掉）
test -e "$AC_HOME/Downloads/新存的文件"      # 期望：存在（探测结束删 upper 后仍在）
# 期望 exit=0；若为 4 且提示"探测未正确共享公共目录"，说明摘出失效、候选已被丢弃（这是正确行为，
# 但说明实现有问题）。**这项检查必须在删 probe/ 之前做**——清理后再去 find probe/upper 永远为空，
# 是个永远通过的空断言（`probe/` 已经不存在了）。
find "$AC_BASE/probe" 2>/dev/null | wc -l   # 期望：0（旧布局的临时区应当从未被创建）
ls /var/tmp/appclone 2>/dev/null | grep -c "probe\."   # 期望：0（探测正常结束后 /var/tmp 里不留 probe.<uid>.<rand>）

# F'. 写层不在 lower 里面（防止 overlay 递归：挂载不报错，但 ls 直接 ELOOP）
#     探测进行中执行：
readlink -f "$PROBE_UPPER" | grep -q "^$(readlink -f "$HOME")/" && echo "上层在 HOME 里，必须失败" || echo ok
# F''. 摘出正向断言（不是只看"探测结果对不对"，而是确认 bind 真的生效）
#     探测会话内执行，逐个公共目录比对源与目标：
findmnt -no SOURCE --target "$HOME/Downloads"   # 期望：真实目录所在设备/路径，不是 overlay/upper

# G. 运行态判定（不靠 pgrep）
appclone run <app> <id> & sleep 3
appclone list <app>                         # 期望：该实例标「运行中」
kill %1; sleep 1
appclone list <app>                         # 期望：不再标运行中（flock 随进程释放）

# H. 审计与 verify（有审计层才有结论，没有就说"不知道"）
appclone run <app> <id> --audit             # 应用内改一条设置后退出
appclone doctor --verify <app> <id>         # 期望：verified 或 leak-detected，**不出现 unverified**
ls "$AC_BASE/instances/<app>/<id>/audit"    # 期望：verified → 只剩 summary.toml；leak/extract_failed → summary.toml + quarantine-*（upper 已被搬走；run.toml 作为本轮凭证留到下次审计开始时被新的进行中凭证覆盖）
appclone doctor --verify <app> <id>; echo $?  # 期望：重放同一结论，退出码与上一次相同（0 或 8）
rm -rf "$AC_BASE/instances/<app>/<id>/audit"   # 模拟"从没开过审计"
appclone doctor --verify <app> <id>         # 期望：unverified + "未开启审计，无法判定"（不是通过）
```

## 8. 高级用法

### 8.1 从主实例数据"克隆起步"（OverlayFS 语义）

新分身可以直接继承主实例现有状态（类似 Android 克隆的复制语义），但**不复制文件**：
`add <app> --fork` 在 `instance.toml` 记 `fork = true`，之后每次 `run` 都为每个档案 `paths`
目录挂一层 fuse-overlayfs——lower 是宿主上的真实数据，upper 是这个分身的 `root/`，
merged 只作 bwrap 的 bind 源。无 root、无特权。

**目录布局与寿命**（混淆就会删掉用户数据）：

| 目录 | 寿命 | 说明 |
|---|---|---|
| `instances/<app>/<id>/root/<原路径>/`（即 upperdir） | **持久** | 分身的真实数据，`gio trash` 之外谁也不许删 |
| `instances/<app>/<id>/.fork/<hash>/work/`（workdir） | 临时 | overlay 内部工作区；必须与 upper 同一文件系统 |
| `instances/<app>/<id>/.fork/<hash>/merged/`（挂载点） | 临时 | 仅挂载期存在；`<hash> = sha256(clean 原路径)[:8]` |

`hash` 用路径哈希而不是数组下标或转义路径：路径含空格/中文时目录名仍稳定，档案顺序变化也不会
让旧挂载点认不出来。

**运行期契约**（`core.Run`，与 CLI/GUI 共用）：

1. `paths` 先按 §5 归一（父子重叠只留最上层），所以每个条目只挂一层，不会嵌套 overlay；
2. **只对宿主上存在且非空、且确实是目录**的条目挂载；空目录/不存在的路径退回普通实例目录
   （挂一份空视图没有收益）；
3. 挂载成功 → bwrap 的 ⑤ 把 merged bind 到原路径；未挂载的路径仍 bind `root/<原路径>`
   （`BuildOptions.ForkSources` 只登记成功的条目）；
4. `shared_writes` 排在 ⑤ 之后，仍 bind 真实宿主文件——「克隆起步」不改变共享语义；
5. run 结束（正常退出、错误、信号、审计收尾）都要卸载；**卸载成功后**才删除
   `.fork/`，卸载失败则保留待下一轮（见第 6、7 条）；
6. **降级不阻断启动**：fuse-overlayfs 不可用、挂载失败、上一轮残留卸不掉时，写一行 stderr
   说明该路径不继承数据，其余照常启动。安全语义不受影响（仍只隔离 `paths`），代价只是
   "少看到主实例的数据"；
7. **残留处理**：上一轮被 SIGKILL 时 `.fork/<hash>/merged` 可能仍挂在 mountinfo 里。
   下一次 run 先扫 `<inst>/.fork/*/merged`，**按 mountinfo 判断**（不能 `stat`：fuse daemon
   已死时 stat 返回 `ENOTCONN`，会被误判成没挂载），卸载成功后才 `RemoveAll`——
   顺序反了会穿过挂载点遍历 lower，删到主实例的真实数据。mountinfo 对空格等字符做
   八进制转义（`\040` 等），判断必须先解码再整串比对，不能拿路径拼字符串做 `Contains`：
   `HOME`/`AC_BASE` 含空格时原样路径永远匹配不上，stale 会被漏判。mountinfo 记录的
   还是**软链解析后**的路径，而调用方手里是词法路径，所以两种形态都要比对（挂载点已死、
   无法 `EvalSymlinks` 时退到最近可解析的祖先再拼回剩余分量）。删除前再做一次
   `mountUnder(base)` 兜底：mountinfo 里仍有 base 之下的挂载点就拒绝 `RemoveAll`。
   **删除实例**（`rm`/GUI 删除）同样先做这套清理；清不干净返回
   `err.instance.fork_cleanup` 并取消删除——带着挂载把实例目录搬进回收站等于把 lower
   视图一起交出去。若旧应用进程还占着挂载，卸载失败就走第 6 条降级，等它退出后的下一轮再清。
8. **挂载活性与递归防护**：挂载轮询要求「mountinfo 有条目 + `stat` 可访问」——fuse daemon
   挂上后立刻崩溃时只有 mountinfo 仍在，不能当成功。若 `upper` 落在 lower 之内
   （`AC_BASE` 位于档案声明的某个目录之下），该路径跳过并告警，否则 overlay 递归。

**语义边界（如实说明）**：lower 是**实时**的主实例数据，不是时间点快照；overlay 的语义
只保证分身自己的写入进 upper，**不保证**分身运行期间主实例同时修改同一份数据时的可见性
（目录项/属性可能不一致，数据库类文件尤其危险）。因此：分身与主实例**不要同时使用**同一
份应用数据；需要"冻结起点"的用户应先把主实例数据复制出来再指定档案。这不在 `--fork`
的承诺里。一旦分身写过某个文件（copy-up），之后只读自己的 upper。

等价命令行（排障用）：

```bash
# 无 root，用 fuse-overlayfs：upper 就是分身的持久数据层，必须落在实例目录的 root/ 下
fuse-overlayfs -o lowerdir="$HOME/.config/WeChat",\
  -o upperdir="$AC_BASE/instances/wechat/work/root/home/u/.config/WeChat",\
  -o workdir="$AC_BASE/instances/wechat/work/.fork/<hash>/work",\
  -o noatime "$AC_BASE/instances/wechat/work/.fork/<hash>/merged"
bwrap --bind / / --bind "$AC_BASE/instances/wechat/work/.fork/<hash>/merged" "$HOME/.config/WeChat" wechat
```

## 9. 局限与风险

- **路径档案需随应用升级维护**：应用改存储位置时分身可能漏隔离——**开启审计**（`run --audit` 或档案 `audit = true`）时，
  `doctor --verify` 能报警并提示重探测，管线重跑即可修复；没开审计时它只能回答"无法判定"，
  不能承诺常态报警（默认关闭审计就是为了不付日常开销，这个代价要说清，不能两样都要）。
- **isolate_dbus 的代价**：私有总线内托盘/通知不可用，适合"能双开 > 桌面集成"的取舍场景；
- **写了 `$HOME` 之外的路径**（如 `/var/lib/x`）：用 `extra_binds` 补；写 `/etc` 的应用已属系统级，不建议分身；
- **系统 keyring / Secret Service 隔离不了**：凭证存在 DBus 服务里，两实例共用同一把钥匙。命中即标 `unsupported`，不要宣称"已隔离"；
- **共享可写文件会互相污染**（最近使用列表、书签、输入法状态）：按 §5.4 列入 `shared_writes` 并在界面提示，不假装隔离；
- **不防检测**：与 Android 系统分身不同，本方案目标是"能用"而非"反检测"，风控型应用（银行类）理论上可经环境探查发现 mount namespace；
- **多实例资源占用**：每个分身是完整进程（含独立渲染进程），内存按实例数增长，与 Android 同理；
- **非特权 user namespace 被禁的环境**（部分企业策略）bwrap 无法运行：明确报错并给检查命令，不做 root fallback；
- **探测能力依赖 fuse**：无 `/dev/fuse` 或未装 `fuse-overlayfs` 的环境只能用 strace 降级路径（覆盖率更低、需要用户配合更久），档案里记录 `probe_method` 以便区分证据强度。
- **探测期只能保证"经过文件系统的写入"**：应用通过 `sudo` 提权写、或写进另一台已挂载的网络盘，不在 overlay 的可见范围；这类情况靠 §9 首条的 `doctor --verify` 兜。
- **运行期审计有性能代价**：`--audit` 把整个 `$HOME` 过一层 overlay，首次打开大文件会 copy-up。默认关闭是刻意的——日常使用不该为验证付税。
- **界面只做中文与英文两种语言**（v1）：消息表在 `core/i18n`（Go map，不用 gettext，与零 cgo 一致），`LANG` 前缀匹配，其他语言回落英文。**界面字符串不得硬编码在 GUI 代码里**——否则加第三种语言要动三屏全部代码。用户数据（实例显示名、应用名）不翻译。
- **GUI 绑定是实验性项目**（puregotk 自述 experimental）：S0 五条验收是准入闸门（第 5 条是 Ubuntu 24.04 实机，见 [tech-stack.md](tech-stack.md) §4.3），不过即回落 gotk4（观感不变，代价是 cgo）。**风险已被隔离在 UI 层，`core` 零感知**——这是"core 与视图分离"在这一层的实际回报。
- **GUI 需要 GTK4/libadwaita 运行库**：非 GNOME 桌面上可能缺，且缺库时 GUI 无法自救提示（init 阶段 dlopen），只能靠发行版包依赖声明保证（`appclone doctor` 仅供开发者与支持场景排障，不是用户路径）。这是选择"零 cgo"换来的代价，如实记录。

## 10. 路线图（Go 唯一实现路径）

按依赖顺序排列，探测先行——它是产品核心价值，也是最大技术风险：

0. **S0 spike（半天）**：30 行 puregotk 程序，验五条——`AdwSwitchRow` 的 `notify::active` 进 Go 回调、`AdwNavigationView` push/pop（**Esc 只关模态/探测页，不承担返回**）、`AdwAlertDialog` 异步 response id、中文与系统暗色，

   **这是 GUI 全部工作的前置闸门**：不过就换 gotk4，其余计划不变（[tech-stack.md](tech-stack.md) §4.3）。
1. **`core` 探测原语**：overlay-diff + whiteout 收集 + 语义分类，拿真实 Electron

7. 档案库社区化（类似 Firejail profile 的分发模式），经 GitHub Releases 分发；格式与运行时档案同一套 TOML，需带 `version` 与校验和，安装时**只写 `profiles/` 模板库、不自动覆盖用户 `profiles.d/`**。

   写层 `upper` 与 `paths`/`shared_writes` 对账；没有审计层时 `verify` 只能输出 `unverified`。
   同期做 `core/i18n` 消息表（zh_CN + en），把 GUI 三屏的字符串从代码里搬出去。

## 11. `core` 包 API 契约（写第一行代码前必须先定）

这一节存在的理由：前 10 节定义的是"系统该怎样"，而 Go 开工第一小时就要面对"函数叫什么、返回什么、错误怎么带码"。
不定这些，CLI 与 GUI 会各自发明一套结构体，双视图契约在第一个功能就分叉。

**模块与依赖（唯一的允许集）**

```
module github.com/mensylisir/appclone        // Go 1.22
core/                 # 不 import cmd/*、不 import cobra、不 import puregotk
core/i18n/            # 消息表（zh_CN + en）
cmd/appclone/         # cobra
cmd/appclone-gui/     # puregotk
profiles/             # 内置模板库，用 //go:embed 编进 core（安装路径无关；见 §6 分发）
```

允许的第三方依赖只有：`spf13/cobra`、`BurntSushi/toml`、`golang.org/x/sys/unix`、
`golang.org/x/text`（**只为 `unicode/norm`**：显示名与重命名的 NFC 归一是 §4 的硬要求，
手写归一化表既不现实也不可能对；不引入它的后果是两个肉眼相同的名字在 GNOME 里并存）。
**TOML 库选 BurntSushi**：`MetaData.Undecoded()` + `map[string]toml.Primitive` 能实现 §5.5 的"未知字段原样保留"；
`pelletier/go-toml/v2` 的 AST 在 `unstable` 包，为 round-trip 引一个不稳定 API 不划算。
**契约允许的损失**：键顺序与注释不保留（要保留注释得自写行级编辑器，不值得）。

**`Env`：core 的依赖注入点**（原函数表把 `LoadProfile(app)` 写成不带上下文的函数，写第一行代码就会撞上
"它从哪儿知道 `AC_BASE`"——只有三条出路：读环境变量、包级单例、或者让 CLI/GUI 各自拼路径，前两条让单测只能串行改环境，
第三条直接违反"路径解析只有一份实现"）

```go
type Env struct {
    Base     string             // AC_BASE 的绝对路径
    Resolver *PathResolver      // §6.4，唯一路径展开实现
    UID      int
    Clock    func() time.Time   // 测试注入；默认 time.Now
    Trasher  func(paths ...string) error // 默认包 gio trash；测试注入以免真的动回收站
    CliPath  string             // 覆盖 CLI 路径（测试注入）；空值走 ResolveCLIPath 三段解析
    AppDirList []string         // 覆盖 .desktop 来源目录（测试注入）；空值走 AppDirs() 三目录
}
func NewEnv() (*Env, error)     // 从真实环境构造（读 AC_BASE/AC_HOME/XDG_*，MkdirAll(Base, 0700)）
```

- **所有读写磁盘的 core 函数都是 `*Env` 的方法**，`Env` 一构造就固定了路径，单测用 `t.TempDir()` 造一个即可，
  不需要 `os.Setenv`（并行测试安全）；
- **`BuildBwrapArgs` 保持纯函数**（不接收 `*Env`，只吃 `BuildOptions`）：它是事实核心，必须能被表驱动测试反复调用；
- CLI 的 `--base` / GUI 的测试开关都只通过构造 `Env` 生效，不许在命令里另算路径。

其余一律是 `*Env` 的方法，例如 `e.LoadProfile("wechat")`、`e.CreateInstance(ctx, "wechat", p, id)`——

**错误契约**（不定义它，CLI 会按字符串分支、GUI 会另写一套中文）

```go
type Error struct {
    Code int      // 与 §6.3 退出码一一对应：2/3/4/5/6/7/8；内部错误 1
    Key  string   // i18n 消息键，如 "err.profile.public_path"
    Args map[string]any
    Err  error    // 可 Unwrap，保留底层原因（os/exec 的 stderr 等）
}
func (e *Error) Error() string { return e.Key }   // 人类文案一律走 i18n，不在 core 拼字符串
func ExitCode(err error) int                      // nil→0；*Error→Code；其他→1
```

- 校验顺序固定：**参数 → 应用/档案 → 环境 → 冲突 → 锁 → 运行态**（同一输入必须永远得到同一个码，
  不能因为"先撞上锁还是先发现档案坏了"而变）；
- CLI 把 `Code` 直接当退出码、把 `Key` 交给 `i18n.T`；GUI 只用 `Key`，不用 `Code`；
- sentinel：`ErrCanceled`（用户取消，`run`/`add` 都返回 0）、`ErrNotRunning`。

**`CreateInstance` 的事务顺序**（原文只有"失败删本次新建的空目录"，不够——中途崩溃会留下
"有实例无档案""有入口无实例"三类半成品）：

1. 全部校验在内存里做完（`ValidateProfile` + `ValidateCreatable`），**一个字节都不写**；
2. 写档案到临时文件（`.tmp.<pid>`），**先不 rename**；
3. `os.Mkdir(instances/<app>/<id>)` —— `EEXIST` 即判重（退出 5），这是唯一的判重依据；
4. 建子目录（`root/`、`locks/`、`instance.toml`，权限见 §4）；
5. 生成 `.desktop` 到临时文件，**先不 rename**；
6. rename 档案 → rename 入口（两个 rename 是提交点，各原子）；
7. 任何一步失败：删掉本次新建的实例目录与入口临时文件，**旧档案保持原样**（不能被改名覆盖）。

**i18n 键命名**：`err.<domain>.<case>` / `ui.<screen>.<element>` / `desktop.clone_name_suffix`。
`core` 只产出键，不产出人类文案；CLI 与 GUI 共用同一张表（否则同一个错误两种说法）。
语言选择规则（ADR-025 补充）：`LC_ALL > LC_MESSAGES > LANG > en`；剥离 `.encoding` 与 `@modifier`，
`-` 归一为 `_`；`zh_CN`/`zh_SG`/`zh_Hans*` → 简体，`zh_TW`/`zh_HK`/`zh_Hant*` → 英文（v1 不做繁体，
